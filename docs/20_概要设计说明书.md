## 1 引言

### 1.1 编写目的

本文承接《智氧青禾—低碳稻作根区氧环境智能预测与加气灌溉调控系统说明书》与《用户手册》所描述的业务需求，给出青禾智灌智慧灌溉管理平台 V1.0 的**总体设计方案**：划分模块边界、定义模块间调用契约、固化 HTTP 与 SocketIO 接口、确定数据模型与关键处理流程，作为详细设计、编码实现、测试用例编写与验收的共同基线。本文不展开到函数级实现细节（见详细设计说明书），但所有模块名、函数名、接口路径、表名、字段名均以当前代码为准。

## 2 总体设计

### 2.1 需求概述

#### 2.1.1 功能需求

| 编号 | 功能 | 验收要点 |
| --- | --- | --- |
| F1 | 多源感知接入 | 经华为云 IoTDA 接收水位、土壤湿度、DO、Eh 四路遥测与双泵状态，单设备 3s 一帧 |
| F2 | 实时看板 | 浏览器经 SocketIO 收到数据后 1s 内刷新数值、泵状态与顶栏连接指示 |
| F3 | RORI 风险评价 | 按 1.3 节公式算 RORI 并分三级（≥70 重度 / 40–70 中度 / <40 安全），给出对应增氧策略 |
| F4 | 降雨前馈动态阈值 | 由 7 日预报算 P6d、α，输出动态上下限，驱动"控水等雨" |
| F5 | 自动调控 | 自动模式下按 RORI 分级控制气泵、按水位阈值控制水泵，状态变化才下发指令 |
| F6 | AI 助手与人机协同预案 | AI 对话问答；AI 生成调控预案，人工确认后下发（HITL） |
| F7 | 告警 | 阈值越限、RORI 越级、设备离线产生告警，去重后落库并转发 webhook |
| F8 | 运行日志 | 系统/设备/自动/手动/配置五类日志统一记录，可查询、可分页 |
| F9 | 历史与导出 | 遥测历史按 user 隔离查询（升序、限量 5000），支持 CSV 导出（UTF-8 BOM） |
| F10 | 配置与账户 | 21 项设备/云平台/第三方配置的读写与掩码保护，账户注册、登录、改密、令牌签发 |

#### 2.1.2 非功能需求（量化指标）

| 编号 | 属性 | 量化指标 |
| --- | --- | --- |
| N1 | 并发 | waitress 8 线程（`FARM_THREADS`，默认 8）；每用户一条 MQTT 连接 + 独立 paho 网络线程；支持 ≥10 台设备 × 3s 上报（约 3.3 帧/秒） |
| N2 | 时延 | MQTT 收包→浏览器可见 ≤1.0s（统一 tick 500ms 合并刷写）；本地 API P95 ≤200ms；AI 对话超时 20s、AI 预案超时 25s |
| N3 | 可用性 | 单机 7×24 运行；MQTT 断线自动重建连接；外部依赖（天气/AI/webhook/逆地理）失效时降级不阻断；历史数据保留 7 天 |
| N4 | 安全 | 密码 PBKDF2 哈希存储；登录失败 5 次锁定 600s；CSP + 4 项安全响应头；SQL 全参数化；密钥仅来自环境变量 |
| N5 | 可维护性 | 单文件 ≤400 行；决策逻辑下沉为无 IO 的纯函数层；模块单向依赖无环；改动以新增文件/蓝图为主 |
| N6 | 可测试性 | `tests/` 用 pytest，`test_auth.py` 40 个用例 + `test_deploy.py` 6 个测试类；纯函数可脱离 Flask 直接测 |
| N7 | 兼容性 | 现代浏览器（Chrome/Edge 100+）；Python 3.10+；Windows 与 Linux 均可部署 |

### 2.2 设计目标与原则

| 原则 | 内涵 | 在代码中的落地证据 |
| --- | --- | --- |
| 分层解耦 | 路由只做参数校验与响应组装，业务在业务模块，SQL 只在 `db.py` | 5 个蓝图不出现裸 SQL；`db.py` 是唯一 `sqlite3.connect` 位置 |
| 纯函数可测 | 算法不依赖全局状态与 IO，输入输出确定 | `qinghe/irrigation.py` 264 行无 IO、无全局状态，可脱离 Flask 单测 |
| 对外契约稳定 | 重构前后接口路径与响应结构逐字不变 | 蓝图均无 `url_prefix`，`/api/*` 路径与旧版 `app.py` 完全一致 |
| 渐进增强 | 新增能力以新文件、新蓝图、新表叠加，不改既有 12 个文件 | 新表在各自模块 `_ensure_schema()` 中 `CREATE TABLE IF NOT EXISTS` 懒建 |
| 失败不升级 | 外部调用失败只降级，不向请求栈抛异常 | `weather.fetch_forecast` 返回 `{'code':'ERR'}`；`ai.chat` 恒返回 `choices` 结构 |

### 2.3 系统总体结构

系统采用六层结构，依赖方向自上而下单向；MQTT 数据流为反向（集成层→业务层→接口层→表现层）。

```
+---------------------------------------------------------------------------------+
| 表现层   templates/index.html + login.html                                      |
|          static/js/{core,store,charts,irrigation,config,ai,weather,realtime,app} |
|          static/css/{base,dashboard,login,modal}                                 |
+---------------------------------------------------------------------------------+
                 |  HTTPS/HTTP  REST      |  WebSocket(socket.io, polling 降级)
+---------------------------------------------------------------------------------+
| 接口层   qinghe/routes/{app,auth,config,data,ai}_routes.py   （5 个蓝图 bp）      |
|          qinghe/realtime.py   SocketIO: connect / send_command / emit hw_data    |
+---------------------------------------------------------------------------------+
                 |  仅向下函数调用，禁止反向 import
+---------------------------------------------------------------------------------+
| 业务层   auth(认证/限流)   iot(MQTT 接入)   irrigation(RORI/阈值/决策)           |
|          alerts(告警判定)  weather(预报/逆地理)  ai(AI 代理)                     |
+---------------------------------------------------------------------------------+
+---------------------------------------------------------------------------------+
| 数据访问层  qinghe/db.py：get_db / init_db / init_geo_cache + 14 个数据访问函数   |
+---------------------------------------------------------------------------------+
                 |  SQL（参数化）
+---------------------------------------------------------------------------------+
| 存储层   SQLite 单文件 qinghe.db（WAL），11 张表                                 |
+---------------------------------------------------------------------------------+
                 ^  MQTT 1883（paho 后台线程，反向数据流）
+---------------------------------------------------------------------------------+
| 集成层   华为云 IoTDA · 和风天气 v7/weather/7d · Photon 逆地理 ·                |
|          DeepSeek chat/completions · 钉钉/企业微信 webhook                        |
+---------------------------------------------------------------------------------+
                 ^  MQTT 上报 / 属性设置下发
+---------------------------------------------------------------------------------+
| 边缘层   FireBeetle ESP32-E（4 路传感器 + 水泵 D9 + 气泵 D5/PWM），上报周期 3s     |
+---------------------------------------------------------------------------------+
```

上图说明：横向是同一层内的并列模块，纵向箭头表示依赖与数据流向。表现层只与接口层通信，业务层不感知 HTTP，数据访问层不感知业务语义，集成层是外部系统的唯一出入口。

各层职责与约束：

| 层 | 职责 | 依赖方向 | 关键约束 |
| --- | --- | --- | --- |
| 表现层 | 数据展示、用户操作、图表渲染、DOM 节流 | → 接口层 | 不拼接未转义数据；定时器统一挂 tick |
| 接口层 | 路由注册、入参校验、鉴权、响应组装 | → 业务层 → 数据层 | 不含业务算法；不直接写 SQL |
| 业务层 | 算法、协议、外部调用、状态机 | → 数据层 → 配置 | 不 import 接口层；异常不外抛 |
| 数据访问层 | 连接管理、建表迁移、DAO | → `config` | 唯一 SQL 出口；参数化 |
| 集成层 | 华为云/天气/AI/webhook 协议适配 | ← 业务层调用 | 全部带 timeout，失败降级 |
| 边缘层 | 采集、执行、断网本地兜底 | 经 MQTT 与集成层交互 | 不在本平台代码范围内 |

### 2.4 运行环境与部署拓扑

```
   学生/管理员浏览器                校园网服务器（Windows/Linux）             华为云
+-------------------+          +--------------------------------+        +-----------+
| Chrome / Edge     |  HTTP    | server.py (waitress, 8 线程)   |  MQTT  | IoTDA     |
| index.html        |<-------->|   └ qinghe.create_app()        |<------>| 设备接入  |
| static/js/*.js    | WebSocket|       ├ routes/*   (5 蓝图)    |  1883  | 规则引擎  |
+-------------------+          |       ├ auth/iot/irrigation    |        +-----+-----+
                               |       └ db.py → qinghe.db(WAL)|              | MQTT
                               +---------------+----------------+              |
                                               | HTTPS 出网           +--------v--------+
                                               v                      | ESP32-E 网关    |
                                 +----------------------------+        | 水位 A0 土壤 A2 |
                                 | 和风天气 / Photon 逆地理   |        | DO A4   Eh A6   |
                                 | DeepSeek API / 钉钉 webhook|        | 水泵 D9 气泵 D5 |
                                 +----------------------------+        +-----------------+
```

上图说明：服务器是被访问的中心节点，浏览器与服务器之间走 HTTP + WebSocket；服务器与华为云之间走 MQTT；所有第三方 HTTP 依赖由服务器出网，浏览器不直连第三方 API。

两种部署形态：

| 形态 | 命令 | 服务器 | 适用 | 关键差异 |
| --- | --- | --- | --- | --- |
| 开发 | `python app.py` | Werkzeug 开发服务器 | 本机调试 | `FARM_DEBUG=1` 时开调试器，热重载；监听 `0.0.0.0:PORT` |
| 生产 | `python server.py` | waitress 多线程 WSGI | 校园网对外开放 | 强制 `async_mode='threading'`；打印本机与校园网访问地址；waitress 缺失时回退 `socketio.run` 并告警 |

两种形态共用同一应用工厂 `qinghe.create_app()`，返回 `(app, socketio)`；`server.py` 的 `load_app()` 优先调用工厂，失败才回退旧单文件入口。

### 3.2 后端模块逐一说明

**config**：全系统唯一常量源，只 `import os`，**不 import 任何其他子模块**，因此不会参与循环依赖。分六组常量：应用与存储（`DB_PATH`、`DB_TIMEOUT=10`、`HISTORY_KEEP_DAYS=7`、`HISTORY_DEFAULT_LIMIT=1000`、`HISTORY_MIN_LIMIT=1`、`HISTORY_MAX_LIMIT=5000`）、安全（`FALLBACK_SECRET_KEY`、`LOGIN_MAX_FAIL=5`、`LOGIN_LOCK_SECONDS=600`、`MASK='••••••••'`、`CSP_POLICY`、`SECURITY_HEADERS`）、量程（`ADC_MAX=4095`、`WATER_FS_MM=300`、`DO_MIN_MGL/DO_MAX_MGL=0/20`、`EH_MIN_MV/EH_MAX_MV=-150/300`）、RORI 权重（`W_EH=0.35`、`W_DO=0.35`、`W_WATER_SOIL=0.30`、`GAMMA=0.5`、`EH_SAFE_MV=300`、`EH_SPAN_MV=450`、`DO_SAFE_MGL=8.0`、`WATER_DEADBAND_MM=5`、`WATER_RISK_SPAN_MM=100`、`RORI_HEAVY=70`、`RORI_MODERATE=40`）、降雨前馈（`RAIN_WEIGHTS`、`H_ROOT=200`、`ALPHA_LOW/MID/HIGH=0.95/0.75/0.45`、`EFF_LOWER_FLOOR=45`、`EFF_UPPER_RAIN=15`、`EFF_UPPER_BONUS=15`、`EFF_UPPER_CAP=100`）、超时（`TIMEOUT_PHOTON=6`、`TIMEOUT_WEBHOOK=6`、`TIMEOUT_WEATHER=8`、`TIMEOUT_AI=20`）。

**db**：封装 SQLite。`get_db()` 每次新建连接并设 `row_factory=sqlite3.Row`、`PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=10000`。`init_db(force=False)` 在模块级 `_init_lock` 保护下建 users/configs/sensor_history/thresh_settings，用 `PRAGMA table_info(configs)` 逐列比对 `_CONFIG_MIGRATIONS`（farm_name、farm_lng、farm_lat、iot_target_device_id、iot_m2m_topic、iot_cmd_topic、webhook_url）补齐旧库字段，并清理 7 天前历史。模块级函数共 17 个（3 个连接/建表函数 + 14 个数据访问函数），覆盖用户、配置（`CONFIG_COLUMNS` 21 列）、历史、阈值、地理缓存；`save_config` 的列名来自常量元组而非用户输入，值一律 `?` 占位。

**auth**：`_login_fail` 字典 + `_login_lock` 实现"用户名 + 客户端 IP"维度的失败计数，键由 `'%s:%s' % (username, ip)` 生成，IP 优先取 `X-Forwarded-For` 首段；窗口过期自动清理。`is_password_hash()` 通过 `('pbkdf2:', 'scrypt:', 'sha256:')` 前缀判断，`verify_password()` 对哈希走 `check_password_hash`、否则退化明文比较以兼容旧库，`authenticate()` 命中明文时自动 `upgrade_plaintext_password()`。`issue_token(uid, days=7)` 以 `current_app.secret_key` 为 HS256 密钥签发；`require_token` 装饰器把 `uid` 作为首参注入被装饰函数。

**iot**：`mqtt_clients` 字典保存每用户连接，`mqtt_lock` 为 `RLock`，`get_client()` 返回副本避免调用方持有内部引用（缺口 G18 已修复）。`connect_huawei_iot(uid)` 先 `_stop_client` 再建连，`mqtt.Client(CallbackAPIVersion.VERSION2, client_id=...)`，`AttributeError` 时回退旧签名。回调链：`on_mqtt_connect` 成功后订阅 `iot_m2m_topic` 与 `$oc/devices/<device_id>/user/#`；`on_mqtt_message` 解码后交 `handle_mqtt_message`；`on_mqtt_disconnect` 置 `connected=False` 并推送离线。`handle_mqtt_message` 只做解析与入队，注释明确"在 MQTT 回调线程中执行，不得做任何阻塞 IO"。

**irrigation**：纯函数层，含 ADC 换算、四个风险因子、`compute_rori`、`classify_rori`、`compute_p6d`、`alpha_of`、`compute_dynamic_threshold`、`decide_control`。`decide_control` 返回结构化决策（`air` / `pump` / `rori` / `level` / `effective_code`），状态未变化时 `pump.command` 为空串，天然实现"变了才下发"。

**alerts**：`evaluate_alerts` 纯判定不落库；`notify_webhook` 拼 `【青禾智灌系统】` 前缀文本，钉钉 `msgtype:text` 载荷，`timeout=6`，非 200/201 视为失败；`AlertDeduper.should_emit(key)` 以冷却窗口（`ALERT_COOLDOWN_SECONDS=60`）去重。

**weather**：`photon_reverse` 调 `https://photon.komoot.io/reverse`，按 state/city/county/district/suburb/quarter 组合最近 4 级行政区名；`geo_key` 用 4 位小数坐标做缓存键，`geo_lookup` 先查 `geo_cache` 再远端；失败时 `geo_fallback_text` 返回 `E: %.2f°, N: %.2f°`。

**ai**：`normalize_base_url` 统一去尾斜杠并把 `http://api.deepseek.com` 强制升为 https；`build_chat_request` 组 `POST {base}/chat/completions`，body 固定 `model=deepseek-chat`、`stream=False`；`chat` 对非 200、非 JSON、网络异常一律 `_wrap()` 成 `choices` 结构返回，绝不抛异常。

**realtime**：`emit_hw_data(uid, payload)` 延迟导入包级 `socketio` 后 `emit('hw_data', payload, room=str(uid))`；`register_events(sock)` 定义 `connect` 与 `send_command`，`connect` 时取会话 `user_id`、`join_room(str(uid))`、触发 `connect_huawei_iot` 并按 `is_connected` 补发上线/离线事件；模块导入时用 `_qinghe_registered` 标记做幂等注册。

**路由层**：5 个蓝图变量名均为 `bp`，注册时不加 `url_prefix`，因此路径与旧版严格一致；统一职责是"取会话 → 校验 → 调业务 → 组装 JSON"。

## 4 接口设计

### 4.1 接口设计约定

| 项 | 约定 |
| --- | --- |
| 风格 | RESTful；资源路径统一以 `/api/` 开头；动作型接口用动词（`/api/plan/confirm`） |
| 请求体 | `application/json`；表单型页面除外 |
| 成功响应 | `{'status': 'success', 'message': '...', ...}`，业务数据挂同级字段 |
| 失败响应 | `{'status': 'error', 'message': '...'}`；404/405 由全局 errorhandler 返回 `{'error': '未找到资源'}` / `{'error': '请求方法不允许'}` |
| 鉴权 | 网页端：会话 Cookie（`session['user_id']`），未登录返回 401 JSON 或 302 重定向；移动端：`Authorization: Bearer <JWT>`，HS256，有效期 7 天 |
| 状态码 | 200 正常（含业务失败也用 200 + `status=error`）；400 入参非法；401 未登录/令牌无效；404 路径不存在；405 方法不允许；429 登录限流；500 未预期异常 |
| 参数校验 | 长度、范围、类型在路由层完成，非法一律 4xx 或回退默认值；SQL 全参数化 |
| 敏感字段 | `iot_pass`、`weather_key`、`ai_key` 在读取时替换为 `MASK='••••••••'`，回写时遇掩码保留旧值 |

### 4.3 SocketIO 事件约定

| 方向 | 事件名 | 载荷 | 触发时机 | 处理要点 |
| --- | --- | --- | --- | --- |
| 下行 | `hw_data` | `{'type':'data','topic':<属性名>,'payload':<值>}` 或 `{'type':'device_status','status':'online'|'offline'}` | MQTT 收到报文、MQTT 连接状态变化 | 按 `type` 分流；`type='data'` 时 `topic` 取属性叶子名（waterlevel/humidity/do/eh/water_pump/air_pump/humi_up/humi_down/waterlevel_up/waterlevel_down/log） |
| 上行 | `send_command` | `{'device':'water_pump'|'air_pump','action':'on'|'off'}` | 用户手动点击或自动调控判定 | 服务端白名单校验后转 `iot.send_property_command` |
| 生命周期 | `connect` / `disconnect` | — | 浏览器建立/断开连接 | `connect` 校验会话、加入 `room=str(uid)`、触发 MQTT 连接、补发在线状态；未登录 `return False` 拒绝 |
| 上行 | `connect_failed` / `disconnect`（前端） | — | 服务不可达 | 前端置 `S.cloudConnected=false`、`S.deviceOnline=false`，写"服务器断开"日志 |

广播按 `room=str(uid)` 隔离，多用户互不串数据。

## 5 数据结构设计

### 5.1 数据库选型与总体设计

选用 **SQLite 单文件 + WAL 日志模式**。理由：① 本系统是单机、单写多读的校园网小规模应用，并发写仅来自遥测落库线程与用户配置保存，WAL 下读不阻塞写、写不阻塞读，`busy_timeout=10000` 足以吸收瞬时冲突；② 零安装零运维，数据库即 `qinghe.db` 一个文件，拷贝即备份，符合课题交付场景；③ 数据量可控——按每设备 3s 一帧、单用户计算，7 天约 20 万行，索引覆盖 `(user_id, ts)` 后查询稳定在毫秒级；④ 与 Python 标准库集成，无额外驱动。代价是不支持跨机共享与高并发写，见 8.1 节权衡。

### 6.4 RORI 计算与分级

| 步骤 | 公式 | 代码位置 |
| --- | --- | --- |
| 1 归一化 | `water_mm = adc/4095×300`；`soil_pct = (4095−adc)/4095×100` | `irrigation.adc_to_water_mm` / `adc_to_soil_pct` |
| 2 Eh 风险 | `S_Eh = clamp((300 − Eh)/450, 0, 1)` | `irrigation.risk_eh` |
| 3 DO 风险 | `S_DO = clamp((8.0 − DO)/8.0, 0, 1)` | `irrigation.risk_do` |
| 4 水/土风险 | `Risk_water = water_mm ≤ 5 ? 0 : clamp((water_mm−5)/100,0,1)`；`Risk_soil = clamp(soil_pct/100,0,1)` | `irrigation.risk_water` / `risk_soil` |
| 5 融合 | `P = 0.35·S_Eh + 0.35·S_DO + 0.30·max(Risk_water,Risk_soil) + 0.5·Risk_water·Risk_soil` | `irrigation.compute_rori` |
| 6 输出 | `RORI = clamp(P,0,1)×100` | 同上 |
| 7 分级 | ≥70 重度厌氧（红）→ 满载强制增氧；40–70 中度缺氧（橙）→ 脉冲加气；<40 安全（绿）→ 低耗待机 | `irrigation.classify_rori` |

流程：收到任一遥测帧 → 前端更新 `S.waterAdc/soilAdc/doValue/ehValue` → tick 内 `updateRori()` 调用 `computeRori` → `classifyRori` 得 `code` → 渲染数值与颜色、更新预警条 → 非手动模式触发 `autoControl(code)`。

### 6.5 6 日降雨前馈动态阈值

```
7 日预报 daily[1..6].precip
        |
        v
P6d = Σ ω_t · P_t        ω = [1.0, 0.9, 0.7, 0.5, 0.4, 0.3]
        |
        v
alpha = P6d ≤ 10 ? 0.95 : (P6d ≤ 50 ? 0.75 : 0.45)
        |
        +--> effLower = max(45, humi_down − alpha·P6d/200×100)
        |
        +--> effUpper = (P6d ≥ 15) ? min(100, humi_up + 15) : humi_up
        |
        +--> rainComing = (预报有效且 P6d ≥ 15)
```

上图说明：P6d 越大说明后续天然降雨越充沛，α 越大表示越"信任"降雨、把下限压得越低，让土壤先消耗现有水分；同时上限放宽以多蓄雨，实现"控水等雨"。下限有 45% 防枯萎保底，上限封顶 100%。

### 6.6 自动调控决策（含滞回去抖）

```
每帧遥测 -> 若 manual_mode=1 则跳过
   |
   v
气泵: effCode = RORI 等级码; 若 rainComing 且 effCode<2 则 effCode+=1
     目标 = effCode>=1 ? 'ON' : 'OFF'
     若 目标 ≠ S.airPumpAutoState 才 emit            <- 状态去抖
   |
   v
水泵: water < wlDown ?
        ├ rainComing -> 'hold'（记录"暂缓补水"日志与告警，不下发）
        └ 否则       -> 'ON'
      water > wlUp   -> 'OFF'
      否则           -> 'ok'（不下发）
     仅当 pumpCmd 非空才 emit
```

上图说明：去抖分两层——气泵按"目标状态是否变化"去重，水泵按"决策是否产生指令"去重（区间内 `'ok'` 不产生指令）。服务端实现（`autocontrol.evaluate`）再加一层时间维滞回（`AUTO_MIN_INTERVAL_SECONDS=60`），防止边界值抖动导致指令风暴。

### 7.1 性能设计

| 手段 | 实现 | 目标值 |
| --- | --- | --- |
| 统一 tick | `core.js` 单主循环 500ms，任务按 500ms/1s/2s/5s/30s 分频，替代多个 `setInterval` | 定时器数量 1；单帧最多一次布局 |

| 批量落库 | `HistoryWriter` 队列 2000、每 1.0s 或 200 条 `executemany` | 写事务 ≤1 次/秒 |
| WAL + 索引 | `journal_mode=WAL`、`busy_timeout=10000`、`idx_history_user_ts` | 单用户 7 天查询 P95 ≤50ms |
| 查询限量 | `_parse_limit` 夹逼 1–5000，默认 1000 | 单次响应 ≤5000 行 |
| 列表渲染上限 | 日志 60 条、告警 30 条，增量 prepend + 裁尾 | DOM 节点数恒定 |
| 连接复用 | 每用户一条 MQTT 连接，`loop_start` 后台线程 | 连接数 = 用户数 |

### 7.2 安全设计

| 威胁 | 措施 | 实现 |
| --- | --- | --- |
| 口令泄露 | 不可逆哈希 | `generate_password_hash`（PBKDF2），旧明文登录时自动升级 |
| 暴力破解 | 登录限流 | 5 次失败锁定 600s，键为"用户名:IP"，支持 `X-Forwarded-For` |
| XSS | 输出转义 | 前端 `esc()` 统一转义 + 全部文本用 `textContent`，不拼 `innerHTML` |
| 点击劫持/嗅探 | 安全响应头 | `after_request` 统一注入 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、CSP |
| SQL 注入 | 参数化 | 全量 `?` 占位；`save_config` 列名来自常量元组 |
| 令牌伪造 | HS256 签名 | 密钥取 `FARM_SECRET_KEY`，缺省时启动打印告警 |
| 密钥外泄 | 掩码 + 环境变量 | 读配置时密钥字段置 `MASK`；回写掩码保留旧值；代码不硬编码 |
| 越权访问 | 会话/令牌双校验 | 每个数据接口按 `session['user_id']` 或 JWT 的 `uid` 过滤 |
| 调试器暴露 | 生产关调试 | `FARM_DEBUG=0`；`server.py` 启动横幅显式告警 |

CSP 策略全文：`default-src 'self'; script-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://cdn.jsdelivr.net; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' https:; font-src 'self' data:; object-src 'none'; base-uri 'self';`

### 7.3 可靠性设计

| 场景 | 机制 |
| --- | --- |
| MQTT 断线 | `on_mqtt_disconnect` 置 `connected=False` 并推送 offline；`connect` 或保存配置时 `connect_huawei_iot` 先 `_stop_client` 再重建，避免连接泄漏 |
| 消息解析失败 | `json.loads` 失败退化为整段字符串，`decode(errors='replace')` 保证不抛 |
| 外部接口失败 | 天气返回 `{'code':'ERR'}`；AI 返回提示文案；webhook 返回 False；逆地理由 `geo_fallback_text` 兜底 |
| 超时控制 | Photon 6s、webhook 6s、天气 8s、AI 20s，全部显式传 `timeout` |
| 脏数据 | 前端限幅：水位 0–300mm、土壤 0–100%、DO 0–20mg/L、Eh −150–300mV；非有限数回退默认 |
| 落库失败 | `flush_once` 把未写入行重新入队，下轮重试 |
| 队列溢出 | `HistoryWriter` 丢最旧并计数；`logbook` 队列满即丢弃新日志，均不影响主流程 |
| 初始化失败 | `run_init_hooks` 捕获异常只告警，不阻断服务启动 |
| 历史膨胀 | `init_db` 每次启动删除 7 天前记录；`prune_alerts`/`prune_logs` 同策略 |

### 7.4 可维护性与可测试性

- **纯函数层隔离**：`irrigation.py` 无 IO、无全局状态，`compute_rori`、`compute_dynamic_threshold`、`decide_control` 可脱离 Flask 直接断言；前端 `irrigation.js` 保持同口径公式，便于对照。
- **模块边界清晰**：业务模块各司单一职责，`db.py` 是 SQL 唯一出口，新增能力以新文件为准（AGENTS.md 约定不改既有 12 个文件）。
- **测试覆盖**：`tests/conftest.py` 提供临时库 fixture，`tests/helpers.py` 封装注册/登录；`test_auth.py` 40 个用例覆盖注册、登录、限流按 IP 隔离、改密、JWT 过期/错签、并发写、WAL 生效；`test_deploy.py` 6 个测试类覆盖环境变量解析、局域网 IP 过滤、启动横幅、密钥生成、批处理脚本与 `load_app`。
- **契约稳定**：接口路径与响应结构重构前后逐字一致，旧版前端可直接运行；错误处理统一由全局 errorhandler 输出 JSON。

## 8 设计权衡与风险

### 8.1 关键权衡

| 决策点 | 选择 | 备选 | 取舍理由 |
| --- | --- | --- | --- |
| 数据库 | SQLite + WAL | PostgreSQL / MySQL | 单机小规模，零运维与单文件交付价值高于并发上限；写并发由队列串行化后不构成瓶颈。若未来多实例部署必须迁移，DAO 层集中便于替换 |
| 实时通道 | SocketIO 长连接 | AJAX 轮询 | 3s 一帧的推送频率下轮询浪费带宽且延迟不可控；SocketIO 自带 polling 降级，waitress 下用 `threading` 模式与 MQTT 线程共存 |
| 调控位置 | 服务端下沉（`irrigation.py` 已有 `decide_control`） | 仅前端调控 | 前端调控无法在无浏览器时执行，也无法审计；下沉后可被 AI 预案与服务端自动调控复用。现状是前端仍为准（见 8.2），属迁移中间态 |
| AI 依赖 | 外部 API + 规则回退 | 本地模型 | 外部 API 质量高、零训练成本；但断网即失效，故预案提供 `decide_control` 规则回退，`ai_used` 字段标明来源 |
| 鉴权 | 会话 + JWT 双轨 | 单 JWT | 网页端复用 Flask 会话最简；移动端无 Cookie 场景需令牌，双轨成本低于统一改造 |
| 边缘自治 | 契约预留、暂不实现 | 立即实现 | 固件不在本次交付范围，服务端先固化 Topic 与指令语义，避免后续返工 |

### 9.3 启动与部署命令

```bash
# 1) 安装依赖
pip install -r requirements.txt

# 2) 生成密钥（写入 .env，服务启动前导出）
python tools/gen_secret.py

# 3) 开发模式（本机调试）
set FARM_DEBUG=1
python app.py

# 4) 生产模式（校园网对外开放，Windows）
set HOST=0.0.0.0
set PORT=5000
set FARM_DEBUG=0
python server.py            # 或双击 start_server.bat

# 5) 放行防火墙端口（管理员权限运行）
firewall_allow.bat
# 等价命令：netsh advfirewall firewall add rule name="QingheFarm" dir=in action=allow protocol=TCP localport=5000

# 6) 停止服务
stop_server.bat             # 或 Ctrl+C

# 7) 运行测试（交付前必须全绿）
python -m pytest tests -q
```

部署后访问：本机 `http://127.0.0.1:5000`，校园网 `http://<服务器IP>:5000`（`server.py` 启动横幅会列出可用地址）。
