## 1 引言

全文的口径是**可验证**：凡给出公式的，必给出算例；凡给出接口的，必给出成功/失败两种响应；凡给出常量的，必给出真实数值与定义位置。文中所有标识符（函数名、字段名、表名、常量名、路由路径）均与源码逐字一致，不做意译。

## 2 设计约定

### 2.1 命名与分层约定

调用方向严格单向，禁止反向依赖：

```
templates/ · static/js/        ← 展示层（Jinja2 + 原生 JS，无构建）
        ↓ HTTP / WebSocket
qinghe/routes/*.py             ← 接口层（Blueprint，只做校验+编排，不写 SQL）
        ↓
qinghe/{irrigation,alerts,planner,metrics,autocontrol}.py   ← 领域层（纯函数优先）
        ↓
qinghe/{db,iot,realtime,weather,ai,auth,alert_center,logbook,heartbeat}.py ← 基础设施层
        ↓
qinghe/config.py               ← 常量层（零内部依赖，禁止 import 其他 qinghe 模块）
```

| 约定 | 规则 | 反例（禁止） |
|---|---|---|
| 模块名 | 全小写，单词间下划线；新增功能模块一律单数名词 | `AlertCenter.py`、`utils2.py` |
| 蓝图变量 | 每个 `routes/*.py` 固定导出 `bp`，蓝图名用短名（`app_api`/`auth_api`/`config_api`/`data_api`/`ai_api`/`monitor`/`insight`/`export`） | 在路由文件里 `app = Flask(...)` |
| 路由路径 | 全路径写死（如 `/api/get_config`），**不使用** `url_prefix`，便于 grep 与旧版逐字对齐 | `@bp.route('/config')` + `url_prefix='/api'` |
| 端点函数名 | `api_xxx` 前缀，与旧版单文件 `app.py` 的函数名保持一致，保证 `url_for('app_api.route_index')` 稳定 | 重命名为 `index_view` |
| 纯函数 | 不碰 DB、不发网络、不读全局状态；输入输出全部由参数与返回值表达 | 在 `compute_rori()` 里查库取 DO 值 |
| DAO 函数 | 一函数一表一动作，返回 `sqlite3.Row` / `Row` 列表 / `None` / `bool` | 在 DAO 里做业务判断 |
| 常量 | 全部集中在 `config.py`；模块私有常量用 `_` 前缀 | 在 `irrigation.py` 里写 `0.35` 字面量 |
| 时间戳 | 一律**毫秒**整数（`int(time.time()*1000)`）；表字段名 `ts` | 秒与毫秒混用 |

### 2.2 统一响应格式与错误码

系统存在两代响应风格，**不可混用**，按接口所属批次区分：

**A. 既有接口（15 个，沿用旧版）**

```json
{"status": "success", "message": "配置已更新"}
{"status": "error", "message": "未知设备"}
```

**B. 新增接口（13 个，NF1–NF7）**

```json
{"status": "success", "count": 3, "alerts": []}
{"error": "limit 必须是 1-500 的整数"}
```

例外（历史遗留，属既有风格但用 `error` 键）：`/api/get_config`、`/api/thresh_settings`、`/api/history`、`/api/forecast`、`/api/reverse_geocode`、`/api/ai_chat` 未登录/未找到时返回 `{"error": "未授权"}` 一类结构。

**错误码总表**

| 状态码 | 触发条件 | 响应体键 | 典型文案（逐字） | 处理方 |
|---|---|---|---|---|
| 200 | 业务成功，或"业务失败但属预期"（如密码错误） | `status`/`message` | `账号或密码错误` | 前端 toast |
| 400 | 入参类型/范围/长度非法；`props` 设备名不在白名单 | `error` 或 `status` | `缺少坐标`、`question 必须是字符串`、`limit 必须是 1-500 的整数` | 前端提示，不重试 |
| 401 | 未登录，或 JWT 缺失/过期/签名错 | `error`/`message` | `未授权`、`未登录`、`未授权访问`、`Token无效或过期` | 前端跳登录 |
| 404 | 资源不存在（配置行、告警 id 不属本人、路由不存在） | `error` | `未找到配置`、`未找到资源` | 前端提示 |
| 405 | 方法不允许 | `error` | `请求方法不允许` | 前端修正调用 |
| 429 | 登录失败次数达阈 | `status`/`message` | `尝试次数过多，请 10 分钟后再试` | 前端倒计时 |
| 500 | 领域层抛异常（新增接口捕获后包装） | `error` | `预案生成失败：<原因>` | 记录日志，前端提示重试 |

注意两个**刻意的非 4xx**：`/api/login` 密码错误返回 200 + `账号或密码错误`（避免前端把 401 当作"会话过期"跳转）；`/api/forecast` 未配 Key 返回 200 + `{"code": "ERR", "error": "未配置天气 API Key"}`（前端按 `code` 判错）。这两处与"非法入参返回 4xx"的约定偏离，理由是不打断页面主流程，**新增接口不得效仿**。

### 2.3 并发与线程模型

Flask 本身无状态，但本系统有三类"外部唤醒"：HTTP 请求、MQTT 回调、SocketIO 事件。三者都可能在任意线程触发领域逻辑，因此并发约束必须显式声明。

**启动形态**：`server.py` 用 waitress（多线程 WSGI，`FARM_THREADS` 默认 8）承载 HTTP；SocketIO 固定 `async_mode='threading'` 走长轮询，**不得**改为 eventlet/gevent——paho-mqtt 的后台线程与 monkey-patch 冲突会导致 emit 静默丢失（`server.py:44-46` 有明确注释）。

**线程清单**

| 线程名 | 数量 | 创建位置 | 职责 | 生命周期 | 阻塞风险 |
|---|---|---|---|---|---|
| waitress worker | 8 | `server.py:281 serve(threads=...)` | 处理全部 HTTP 请求 | 进程级 | 外部 HTTP 调用已设 timeout |
| SocketIO 事件线程 | 按连接 | Flask-SocketIO（threading 模式） | `connect`/`send_command` 回调 | 连接级 | `connect_huawei_iot` 内含 TCP 建连，可能耗秒级 |
| paho loop 线程 | 每用户 1 | `iot.py:357 cli.loop_start()` | 收 MQTT 报文 → `on_mqtt_message` | 连接级 | 回调内**禁止**阻塞 IO |
| `history-writer` | 1（守护） | `iot.py:157` | 每 1.0 s 批量写 `sensor_history` | 进程级 | 单批 ≤200 行 |
| `logbook-writer` | 1（守护） | `logbook.py` `_LogWriter._run` | 每 1.0 s 或满 20 条批量写 `logs` | 进程级 | 队列满丢最旧 |
| `alert-push` | 每条告警 1（守护） | `alert_center.py:166 push_alert()` 内 `threading.Thread` | webhook 推送，重试 2 次（0.5 s/1.0 s 退避） | 秒级 | `timeout=6` |
| `heartbeat-watcher` | 0 或 1 | `heartbeat.start_watcher()`（默认**不自动启动**） | 每 5 s 扫描离线并广播 | 显式启停 | 批量 UPDATE |

**共享状态与锁**

| 状态 | 位置 | 保护方式 | 读写方 |
|---|---|---|---|
| `mqtt_clients` | `iot.py:28` | `mqtt_lock = RLock` | 请求线程、MQTT 回调 |
| `_login_fail` | `auth.py:19` | `_login_lock = Lock` | 登录/App 登录请求 |
| `HistoryWriter.queue` | `iot.py:94` | `queue.Queue` 内部锁 + `put_nowait` | MQTT 回调写、writer 读 |
| `_writer`（logbook） | `logbook.py` | `_DB_LOCK` + 队列 | `add_log` 写、writer 读 |
| `_schema_ready`（NF 模块） | 各模块 | `_schema_lock` | 首次调用建表 |
| `_last`（metrics 泵状态） | `metrics.py:46` | `_last_lock` | `note_pump_state` |
| `socketio` 单例 | `qinghe/__init__.py:18` | 进程级单例，`init_app` 一次 | 全部 emit |

**关键规则**：MQTT 回调线程只允许做「解析 + emit 入队 + 历史入队」三件事，任何落库都通过队列交给 `history-writer`；`handle_mqtt_message()` 的 docstring 明确写死此约束（`iot.py:243-247`）。违者表现为设备高频上报时页面卡顿、`database is locked` 频发。

**已知并发缺陷**：`planner`/`autocontrol`/`metrics` 的运行态（`_latest`、`state_json`、`_last`）保存在**进程内存**。waitress 单进程多线程下正确；一旦改为多进程（gunicorn 多 worker）会出现同一用户在不同 worker 看到不同状态。当前部署形态（单进程多线程）不触发，属于设计边界而非 bug，实施多进程前必须外移到 DB 或 Redis。

### 2.4 防御式编程约定

| 场景 | 约定 | 实现样例 |
|---|---|---|
| 数值入参 | 先 `float()`/`int()`，异常返回默认值而非抛出 | `irrigation.py:19-25` `except (TypeError, ValueError): return 0.0` |
| 数据库连接 | 一律 `with closing(get_db()) as conn:` | `db.py` 全部 DAO |
| 外部网络 | 必设 `timeout`，异常吞掉返回兜底值 | `weather.py:98 timeout=8`；`ai.py:54 timeout=20` |
| 迁移 | `ALTER TABLE` 前先 `PRAGMA table_info` 判断列是否存在 | `db.py:68-72` |
| 建表 | 新增模块用懒建 + 幂等标志，避免启动顺序依赖 | `alert_center.py:68 _ensure_schema()` |
| 敏感字段回显 | 非空即掩码 `config.MASK`，不返回明文 | `config_routes.py:38-40` |
| 用户输入拼接 SQL | 只允许 `?` 参数化；**例外**：`save_config` 的列名来自常量元组 `CONFIG_COLUMNS`（非用户输入） | `db.py:219-222` |
| 前端渲染 | 用户/设备数据禁止进 `innerHTML`；走 `textContent` 或 `esc()` | `core.js:46-50`、`app.js:57-69` |
| 入参长度 | 字符串类入参一律显式截断或拒绝 | `data_routes.py:86` `msg[:500]`；`insight_routes.py:77` `>500` 拒绝 |

## 4 数据访问层详细设计（`qinghe/db.py`）

### 4.1 连接管理

`get_db() -> sqlite3.Connection` 每次调用新建连接，三件事固定：

1. `sqlite3.connect(config.get_db_path(), timeout=config.DB_TIMEOUT)` —— 路径**每次动态读**，因此测试用 `FARM_DB_PATH` 切库无需重启进程；
2. `conn.row_factory = sqlite3.Row` —— DAO 统一返回可按列名取值的 `Row`；
3. `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=10000` —— WAL 让读不阻塞写，`busy_timeout` 把"短暂锁冲突"变成等待而非立即 `database is locked`。两条 PRAGMA 包在 `try/except sqlite3.Error: pass` 内，因为内存库或只读介质可能不支持。

**连接所有权**：函数不缓存连接，调用方必须 `with closing(get_db()) as conn:`（`closing` 保证异常路径也 `close()`）。这是全项目唯一的连接获取入口，`sqlite3.connect` 在 `qinghe/` 内只出现一次。

### 4.2 幂等迁移

```
init_db(force=False):
  1. with _init_lock:                       # 进程级互斥，防多线程重复建表
  2.   if _initialized and not force: return
  3.   conn = get_db()
  4.   CREATE TABLE IF NOT EXISTS users / configs / sensor_history / thresh_settings
  5.   PRAGMA table_info(configs) -> 现有列名集合
  6.   for (col, ddl) in _CONFIG_MIGRATIONS: 若 col 不在集合，执行该 ALTER TABLE
  7.   CREATE INDEX IF NOT EXISTS idx_history_user_ts ON sensor_history(user_id, ts)
  8.   DELETE FROM sensor_history WHERE ts < now_ms - HISTORY_KEEP_DAYS*86400000
  9.   _initialized = True
```

| 机制 | 实现 | 为什么这样 |
|---|---|---|
| 一次性标记 | 全局 `_initialized: bool` + `_init_lock` | 首请求并发时十个线程同时进来只建一次表 |
| 增量迁移 | `_CONFIG_MIGRATIONS` 列表（列名, DDL），先查 `table_info` 再 `ALTER` | 老库升级不丢数据，且 SQLite 的 `ADD COLUMN` 不可重复执行 |
| 强制重跑 | `force=True` 忽略 `_initialized` | 测试用例切库后需要在新库建表 |
| 历史清理 | 启动时按 `HISTORY_KEEP_DAYS` 删除 | 避免 `sensor_history` 无限增长拖慢查询 |
| `geo_cache` 独立 | `init_geo_cache()` 单独函数、单独调用 | 它是缓存表，允许在只读场景不建 |

## 5 核心算法详细设计（`qinghe/irrigation.py`）

本模块是纯函数层：264 行、零 IO、零全局状态，输入参数 → 输出字典，因此可被单测穷举、被前端逐字复刻。前端 `static/js/irrigation.js` 与 `templates/index.html` 内的同名实现必须与本模块口径一致，任何一侧改动都要同步另一侧。

### 5.1 变量与符号

| 符号 | 代码标识 | 物理含义 | 量程 |
|---|---|---|---|
| W_adc | `water_adc` | 探针水位 ADC，越高越深 | 0–4095 |
| S_adc | `soil_adc` | 电容土壤 ADC，越高越干 | 0–4095 |
| WaterA0 | `water_mm` | 水位（mm） | 0–300（`WATER_FS_MM`） |
| %RH | `soil_pct` | 土壤湿润度（%） | 0–100 |
| DO | `do_mgl` | 根区溶解氧（mg/L） | 0–20 |
| Eh | `eh_mv` | 氧化还原电位（mV） | −150–300 |
| P6d | `p6d` | 时间衰减加权 6 日累计雨量（mm） | ≥0 |

### 5.2 量程换算

```
adc_to_water_mm(water_adc):
  1. try: mm = float(water_adc) / 4095.0 * 300.0
  2. except (TypeError, ValueError): return 0.0            # None/''/'abc' 一律当 0
  3. return clamp(mm, 0.0, 300.0)                           # 超量程截断

adc_to_soil_pct(soil_adc):
  1. try: pct = (4095.0 - float(soil_adc)) / 4095.0 * 100.0 # 取反：ADC 高 → 干
  2. except: return 0.0
  3. return clamp(pct, 0.0, 100.0)
```

`clamp(value, low, high) = max(low, min(value, high))`，三处归一化都复用它，避免各写一遍边界。

### 5.3 四个风险因子

| 函数 | 公式 | 定义域处理 | 边界行为 |
|---|---|---|---|
| `risk_eh(eh_mv)` | S_Eh = clamp((300 − Eh) / 450, 0, 1) | Eh=300 → 0；Eh=−150 → 1；Eh>300 → 0 | 越界被 clamp 吸收，不抛异常；`float()` 失败会抛（调用方保证数值） |
| `risk_do(do_mgl)` | S_DO = clamp((8.0 − DO) / 8.0, 0, 1) | DO=8.0 → 0；DO=0 → 1；**DO>8.0 mg/L → 负数 → clamp 到 0** | "超 8.0 mg/L 规则"即高氧不产生风险，无需单独分支 |
| `risk_water(water_mm)` | 若 WaterA0 ≤ 5.0 返回 0；否则 clamp((WaterA0 − 5) / 100, 0, 1) | 死区 5 mm 内视为无渍水风险；105 mm 即满风险 | 先判死区再归一，避免 0–5 mm 内产生 0.01 级噪声 |
| `risk_soil(soil_pct)` | R_soil = clamp(%RH / 100, 0, 1) | 越湿风险越高（与水位同向） | 直接线性，不设死区（有 RORI 耦合项兜底） |

`risk_do` 的分子分母都用了 `DO_SAFE_MGL`（而非 `DO_MAX_MGL`），这是刻意的：设计上"8 mg/L 以上即视为充分供氧"，20 mg/L 只是传感器量程上限，不参与归一化。若误把分母改成 20，则 DO=6 时风险会从 0.25 掉到 0.10，导致 RORI 系统性偏低，属于高危改动。

### 5.4 `compute_rori`：多维融合

**公式**

```
P = W_EH·S_Eh + W_DO·S_DO + W_WATER_SOIL·max(R_water, R_soil) + GAMMA·R_water·R_soil
RORI = clamp(P, 0, 1) × 100
```

**伪代码（编号步骤）**

```
1. water_mm  = adc_to_water_mm(water_adc)
2. soil_pct  = adc_to_soil_pct(soil_adc)
3. s_eh      = risk_eh(eh_mv)
4. s_do      = risk_do(do_mgl)
5. r_water   = risk_water(water_mm)
6. r_soil    = risk_soil(soil_pct)
7. p = 0.35*s_eh + 0.35*s_do + 0.30*max(r_water, r_soil) + 0.5*r_water*r_soil
8. return clamp(p, 0.0, 1.0) * 100.0
```

**设计意图**：第 7 步的 `max()` 项表达"渍水与湿土只要其一成立即构成缺氧环境"，不重复计罚；耦合项 `r_water·r_soil` 表达"既渍水又高湿"的乘性恶化——两项同时接近 1 时额外贡献 0.5，是唯一可能把 P 推过 0.7 的耦合来源。四项系数之和 > 1（0.35+0.35+0.30+0.5=1.5），所以 P 会饱和，最后的 `clamp` 是必需的而非装饰。

**算例一（本章指定算例）**

输入：`water_adc=1500`、`soil_adc=2200`、`do_mgl=6.0`、`eh_mv=120`。

| 步骤 | 计算 | 结果 |
|---|---|---|
| 量程换算 | 1500/4095×300 | WaterA0 = **109.89 mm** |
| 量程换算 | (4095−2200)/4095×100 | %RH = **46.28%** |
| S_Eh | (300−120)/450 | **0.4** |
| S_DO | (8.0−6.0)/8.0 | **0.25** |
| R_water | (109.89−5)/100 = 1.0489 → clamp | **1.0** |
| R_soil | 46.28/100 | **0.4628** |
| 加权项 | 0.35×0.4 | 0.1400 |
| 加权项 | 0.35×0.25 | 0.0875 |
| 加权项 | 0.30×max(1.0, 0.4628) | 0.3000 |
| 耦合项 | 0.5×1.0×0.4628 | 0.2314 |
| 求和 | 0.1400+0.0875+0.3000+0.2314 | P = 0.7589 |
| 输出 | 0.7589×100 | **RORI = 75.89** |

分级：75.89 ≥ 70 → `code=2`、`name='重度厌氧'`、策略"重度厌氧预警，加气机全满载强制增氧"。

**边界与异常用例**

| 用例 | 输入 | 期望 | 依据 |
|---|---|---|---|
| 全安全 | adc=(0,4095)、DO=8.0、Eh=300 | RORI=0.00 | 四个因子全 0 |
| 全危险 | adc=(4095,4095)、DO=0、Eh=−150 | P=1.5 → clamp → RORI=100.00 | 饱和截断 |
| 高氧 | DO=12.0 | S_DO=0（负数被 clamp） | "超 8.0 即无风险" |
| 死区 | WaterA0=4.0 | R_water=0 | 5 mm 死区 |
| 入参为 `None`/`''` | `water_adc=None` | WaterA0=0，不抛异常 | `except` 兜底 |
| 入参为 `'abc'` | `water_adc='abc'` | WaterA0=0 | 同上 |
| 超量程 | `water_adc=9000` | WaterA0=300.0 | clamp |

### 5.5 `classify_rori`：三分档

| RORI 区间 | `code` | `name` | `strategy`（逐字） |
|---|---|---|---|
| ≥70 | 2 | 重度厌氧 | 重度厌氧预警，加气机全满载强制增氧 |
| 40 ≤ RORI < 70 | 1 | 中度缺氧 | 根区微量缺氧，周期性脉冲加气补氧 |
| < 40 | 0 | 安全运行 | 根区有氧环境优良，加气机低耗待机 |

判定顺序是先 `>=RORI_HEAVY` 再 `>=RORI_MODERATE` 再兜底，因此 70 与 40 两个边界都归入**上档**（`75.89` 落在重度、`40.0` 落在中度）。前端 `classifyRori()` 必须保持同样的 `>=` 方向。

### 5.6 降雨前馈：`compute_p6d` / `alpha_of`

```
compute_p6d(daily_precips):
  1. total = 0
  2. for i, precip in enumerate(daily_precips or []):
  3.     if i >= 6: break                       # 只取前 6 日
  4.     try:    total += RAIN_WEIGHTS[i] * (float(precip) or 0.0)
  5.     except (TypeError, ValueError): continue    # 单项脏数据跳过，不整体失败
  6. return total
```

| 函数 | 分段 | 返回 |
|---|---|---|
| `alpha_of(p6d)` | `p6d ≤ 10.0` | `0.95` |
| | `10.0 < p6d ≤ 50.0` | `0.75` |
| | `p6d > 50.0` | `0.45` |

α 随雨量递减的物理含义：雨越大，土壤持水能力越接近饱和，后续降雨中能被作物真正利用的比例越低，因此按 0.95→0.75→0.45 三档折减。

### 5.7 `compute_dynamic_threshold`

```
1. fc      = list(daily_precips or [])
2. p6d     = compute_p6d(fc)
3. alpha   = alpha_of(p6d)
4. effLower = max(45.0, humi_down - (alpha * p6d / 200.0) * 100.0)
5. effUpper = min(100.0, humi_up + 15.0)  if p6d >= 15.0  else humi_up
6. return {P6d, alpha, effLower, effUpper, baseLower: humi_down,
           baseUpper: humi_up, hasForecast: len(fc) > 0, rainComing: p6d > 0}
```

| 输出字段 | 含义 | 与入参关系 |
|---|---|---|
| `P6d` | 加权 6 日雨量 | 单调不减于每日雨量 |
| `alpha` | 有效利用系数 | 三档阶梯 |
| `effLower` | 灌溉触发下限（下调） | 恒 ≥45.0（保底），且恒 ≤ `baseLower` |
| `effUpper` | 蓄雨上限（上调） | P6d≥15 时 +15，封顶 100 |
| `baseLower` / `baseUpper` | 用户原始设定 | 原样透传 |
| `hasForecast` | 是否拿到预报 | `len(fc)>0` |
| `rainComing` | 是否"有雨可等" | `P6d>0`，注意不是 `>15` |

两个细节：`effLower` 的 `max(45.0, ...)` 是防枯萎保底——即使预测大雨也不允许把下限压到 45 以下；`rainComing` 用 `P6d>0` 而非 `≥15`，是为了让"毛毛雨"也能触发水泵 `hold`（暂缓补水），而 `effUpper` 只在 ≥15 mm 时才放宽（避免小雨就蓄水导致内涝）。

**算例二（本章指定算例）**

输入：6 日降雨 `[0, 8, 20, 5, 12, 3]`，用户阈值 `humi_down=40`、`humi_up=80`。

| 日序 | P_t (mm) | ω_t | 贡献 |
|---|---|---|---|
| 1 | 0 | 1.0 | 0.00 |
| 2 | 8 | 0.9 | 7.20 |
| 3 | 20 | 0.7 | 14.00 |
| 4 | 5 | 0.5 | 2.50 |
| 5 | 12 | 0.4 | 4.80 |
| 6 | 3 | 0.3 | 0.90 |
| 合计 | 48（未加权） | — | **P6d = 29.40 mm** |

| 输出 | 计算 | 结果 |
|---|---|---|
| α | 10 < 29.40 ≤ 50 → 取 `ALPHA_MID` | **0.75** |
| effLower | max(45, 40 − (0.75×29.40/200)×100) = max(45, 40 − 11.025) | **45.00** |
| effUpper | 29.40 ≥ 15 → min(100, 80+15) | **95.00** |
| hasForecast / rainComing | — | `True` / `True` |

结论：该日土壤湿度低于 45.0% 才触发灌溉（原设定 40%，因保底反而**抬高** 5 个百分点）；高于 95.0% 才判"过高"（原 80%，放宽 15 个百分点）。这正是"控水等雨 + 蓄雨"策略在数值上的体现。

### 5.8 `decide_control`：自动调控

**输入**

| 参数 | 类型 | 说明 |
|---|---|---|
| `water_mm` | float | 当前水位 |
| `soil_pct` | float | 当前土壤湿润度 |
| `rori` | float | RORI 指数 |
| `thresholds` | dict | 至少含 `waterlevel_down`、`waterlevel_up`，缺省回退 `THRESH_DEFAULTS` |
| `state` | dict 或 None | 上一轮 `{'pump': 'on'|'off'|'hold'|'ok', 'air': 'ON'|'OFF'}` |
| `dt` | dict 或 None | `compute_dynamic_threshold()` 的输出 |

**输出**

```
{'air':  {'state': 'ON'|'OFF', 'changed': bool, 'reason': str},
 'pump': {'state': 'on'|'off'|'hold'|'ok', 'command': 'ON'|'OFF'|'', 'changed': bool, 'reason': str},
 'rori': float, 'level': {...}, 'effective_code': int}
```

**伪代码**

```
1. level = classify_rori(rori); eff_code = level['code']
2. if dt.rainComing and eff_code < 2: eff_code += 1        # 降雨前馈提前一级增氧
3. air_new = 'ON' if eff_code >= 1 else 'OFF'
4. air_changed = (state.get('air') != air_new)
5. if   water < wl_down: new_state, cmd = ('hold', '') if dt.rainComing else ('on', 'ON')
6. elif water > wl_up:   new_state, cmd = ('off', 'OFF')
7. else:                 new_state, cmd = ('ok', '')
8. pump_changed = (state.get('pump') != new_state)
9. if not pump_changed: cmd = ''                            # 状态未变不下发
10. return {air:{state,changed,reason}, pump:{state,command:cmd,changed,reason}, ...}
```

**决策真值表**

| 水位条件 | 是否有雨 `rainComing` | 泵 `state` | 泵 `command`（changed 时） | 语义 |
|---|---|---|---|---|
| `water < wl_down` | False | `on` | `ON` | 触发灌溉 |
| `water < wl_down` | True | `hold` | `''` | 前馈控水等雨，暂缓补水 |
| `wl_down ≤ water ≤ wl_up` | 任意 | `ok` | `''` | 滞回区间，待命 |
| `water > wl_up` | 任意 | `off` | `OFF` | 排水/停灌 |

| RORI 档 | `level.code` | `rainComing` | `effective_code` | 气泵 `state` |
|---|---|---|---|---|
| 安全 | 0 | False | 0 | `OFF` |
| 安全 | 0 | True | **1** | `ON` |
| 中度 | 1 | False | 1 | `ON` |
| 中度 | 1 | True | **2** | `ON` |
| 重度 | 2 | 任意 | 2（不再加） | `ON` |

**滞回（hysteresis）的落地方式**：`wl_down` 与 `wl_up` 之间构成一个宽度为 `wl_up−wl_down`（默认 120 mm）的死区，水位在区间内不产生任何指令，从而避免"补水→超上限→关机→回落"的高频振荡。第二层滞回在"仅状态变化才下发"：即使同一档位反复成立，`changed=False` 时 `command` 被强制置空，MQTT 不会被刷屏。气泵同理，靠 `state.get('air')` 比对。

**算例二续（用同一组数）**：`water_mm=109.89`、`rori=75.89`、`rainComing=True`、阈值默认 30/150 → `effective_code=2`（≥2 不再加）→ 气泵 `ON`；水位 109.89 落在 [30,150] → 泵 `ok`、`command=''`。若水位改为 20 mm，则因 `rainComing` 走 `hold` 分支，理由串为"水位 20.0mm < 下限 30mm，但预测降雨 P6d=29.4mm，暂缓补水"。

## 6 认证与安全详细设计（`qinghe/auth.py`）

### 6.1 密码哈希与透明升级

| 函数 | 行为 |
|---|---|
| `is_password_hash(stored)` | 前缀命中 `('pbkdf2:', 'scrypt:', 'sha256:')` 即为哈希，否则视为旧库明文 |
| `verify_password(stored, password)` | 哈希走 `check_password_hash`；明文走 `==` |
| `upgrade_plaintext_password(uid, password)` | `db.update_password(uid, generate_password_hash(password))` |
| `hash_password(password)` | 注册/改密统一入口 |
| `authenticate(username, password)` | 取用户行 → 校验 → **命中明文时自动升级为哈希** → 返回 `(user_row, ok)` |

透明升级的意义：历史库里的明文口令不需要一次性迁移脚本，用户下次登录成功即自动变哈希，失败则保持原样。代价是首次登录有一次 `UPDATE` 写操作，可接受。

### 6.2 登录限流

| 项 | 实现 |
|---|---|
| 限流键 | `'%s:%s' % (username, _client_ip())`，即 **用户名+IP**，不是纯 IP（避免同一 NAT 出口互相拖累），也不是纯用户名（避免攻击者锁死他人账号） |
| 取 IP | `X-Forwarded-For` 首段优先，否则 `request.remote_addr or 'unknown'` |
| 计数结构 | `_login_fail = {key: (count, last_ts)}` |
| 线程安全 | `_login_lock = threading.Lock()`，四个操作全部持锁 |
| 判定 | `_login_locked()`：窗口 `LOGIN_LOCK_SECONDS=600` 过期即清并放行；未过期则 `count >= LOGIN_MAX_FAIL=5` 判锁 |
| 记失败 | `_record_login_fail()`：窗口内累加并刷新 `ts`，窗口外重置为 1 |
| 清计数 | `_clear_login_fail()`：登录成功立即清 |
| 测试钩子 | `reset_login_failures()`：清空全表 |

滑动窗口而非固定窗口：每次失败都刷新 `ts`，所以持续攻击永远不会解锁；正常用户停手 10 分钟后自动恢复。锁定响应为 429 + `尝试次数过多，请 10 分钟后再试`（`auth_routes.py:40`）。

### 6.3 JWT

| 项 | 取值 |
|---|---|
| 算法 | `HS256`（`issue_token` 显式传 `algorithm='HS256'`，`require_token` 解码时 `algorithms=['HS256']` 白名单） |
| 载荷 | `{'user_id': uid, 'exp': utcnow + 7 days}`，不含用户名/角色 |
| 密钥 | `current_app.secret_key`，即 `config.get_secret_key()` |
| 有效期 | 7 天（`issue_token(uid, days=7)`） |
| 提取 | 仅 `Authorization: Bearer <token>`，不支持 query/body 传参 |
| 失败 | 缺失 → 401 `{'status':'error','message':'未授权访问'}`；解码异常 → 401 `{'status':'error','message':'Token无效或过期'}` |
| 注入 | 装饰器把 `uid` 作为被装饰函数的首个位置参数：`f(uid, *args, **kwargs)` |

JWT 只服务于 App 端（`/api/app_login` 签发，`/api/app_send_command` 消费）。网页端用 Flask session（签名 Cookie），两条通道**互不复用**：网页接口不认 JWT，App 接口不认 session。

### 6.4 会话与 CSRF 现状

| 项 | 现状 | 风险与说明 |
|---|---|---|
| 会话载体 | Flask 默认签名 Cookie，存 `user_id`、`username` | 密钥泄露即可伪造，故强制生产设 `FARM_SECRET_KEY` |
| Cookie 属性 | 未显式设置 `SameSite`/`Secure`/`HttpOnly` | Flask 默认 `HttpOnly=True`；`SameSite` 未设为 Lax 的显式声明，依赖浏览器默认（现代浏览器默认 Lax） |
| CSRF 防护 | **无 CSRF Token** | 依赖同源策略 + `SameSite` + 全部写接口要求 `Content-Type: application/json`（跨站表单无法直接构造 JSON 请求） |
| 兜底告警 | `__init__.py:_warn_default_secret()` | 使用兜底密钥且非 debug 时打印 78 个星号 + 警告文案 |

这是一处**已知的、有意的取舍**：项目为单机/校园网部署，未引入 Flask-WTF。若对外开放到公网，必须补 `SameSite=Lax; Secure` 与 CSRF Token（登记于第 16 章）。

### 6.5 安全响应头与 CSP

见 3.3 的逐项表。实现方式为 `after_request` 全局钩子，对**所有**响应生效（含 JSON、CSV、页面）。CSP 中 `connect-src 'self' https:` 是为了允许 SocketIO 长轮询与未来可能的 HTTPS 上游；`img-src 'self' data:` 允许内联 base64 图与图表导出。

## 7 设备接入层详细设计（`qinghe/iot.py`）

### 7.1 连接注册表

```
mqtt_clients = {
  uid: {'client': mqtt.Client, 'device_id': str, 'cmd_topic': str, 'connected': bool}
}
mqtt_lock = threading.RLock()
```

| 函数 | 行为 | 锁 |
|---|---|---|
| `get_client(uid)` | 返回记录的**浅拷贝** `dict(entry)`，调用方改副本不影响注册表 | 持锁 |
| `is_connected(uid)` | 只有 `connected=True` 才算连上（不是"有 client 对象"） | 持锁 |
| `set_connected(uid, bool)` | 仅当记录存在时改标记 | 持锁 |
| `_stop_client(uid)` | **先 pop 再 stop**，避免回调线程在 stop 过程中再次读到该记录；`loop_stop()`/`disconnect()` 各自 try/except | pop 持锁，stop 不持锁 |
| `clear_clients()` | 取 uid 快照后逐个停（测试/退出用） | 快照持锁 |

用 `RLock` 而非 `Lock`：`connect_huawei_iot` 会先调 `_stop_client`（内部持锁），再在结尾持锁写入，若中间有嵌套调用同一线程会自死锁，`RLock` 允许重入。

### 7.2 `HistoryWriter`：队列批量落库与背压

```
enqueue(uid, ts, water_adc, soil_adc):
  1. try queue.put_nowait(item) -> True
  2. except Full:
  3.     try queue.get_nowait(); dropped += 1        # 丢最旧
  4.     except Empty: pass
  5.     try queue.put_nowait(item) -> True
  6.     except Full: dropped += 1; return False     # 极端情况丢新
```

| 参数 | 值 | 来源 |
|---|---|---|
| 队列容量 | 2000 | `HISTORY_QUEUE_MAX` |
| flush 周期 | 1.0 s | `HISTORY_FLUSH_INTERVAL` |
| 单批上限 | 200 行 | `HISTORY_FLUSH_BATCH` |
| 线程名 | `history-writer`，daemon | `iot.py:158` |

**背压策略是"丢最旧、绝不阻塞"**：MQTT 回调线程一旦阻塞，paho 的接收缓冲会堆积，最终导致设备端重传雪崩。因此队列满时宁可丢一条历史采样（`dropped` 计数可观测），也不让回调等待。`flush_once()` 在 `db.insert_history_rows` 抛异常时把整批**重新入队**并返回 0，实现"落库失败不丢数据、下次重试"；但重新入队同样可能因队满而丢弃，这是可接受的降级。

`_run()` 用 `self._stop.wait(interval)` 而非 `time.sleep`，使 `stop()` 能立即唤醒线程；`stop()` 先 `set()` 再 `join(2.0)` 再补一次 `flush_once()`，保证进程退出前把队列排空。

### 7.3 `handle_mqtt_message`：三种报文分支

`parse_mqtt_payload(topic, content) -> (topic_leaf, values, messages)`：

| 分支 | 判定条件 | `values` | `messages` |
|---|---|---|---|
| A 华为云物模型 | JSON 且含 `services` | 遍历 `services[].properties` 的标量 | 每条属性一条 `{'type':'data','topic':属性名,'payload':str(v)}` |
| B 自定义 JSON | JSON 对象且非空、无 `services` | 直接收 `int/float/str/bool` 值 | 同上 |
| C 纯文本 | 非 JSON 或解析失败 | 空 | 单条 `{'type':'data','topic':topic_leaf,'payload':content}` |

`topic_leaf = topic.split('/')[-1]` 在三种分支下都先算好，供分支 C 与日志使用。JSON 解析失败**不中止**，直接降级为 C，保证设备端发半包/乱码时仍能看到原始内容。

**限幅表（前端与后端双重限幅）**

| 量 | 报文键 | 后端限幅 | 前端限幅（`realtime.js`） |
|---|---|---|---|
| 水位 ADC | `waterlevel` | `int(float(v))` | `Math.max(0, Math.min(round(adc/4095*300), 300))` → mm |
| 土壤 ADC | `humidity` | 同上 | `Math.max(0, Math.min(round((4095-adc)/4095*100), 100))` → % |
| 溶解氧 | `do` | 不落库，仅推送 | `clamp(doRaw, 0, 20)` |
| 氧化还原电位 | `eh` | 不落库，仅推送 | `clamp(ehRaw, -150, 300)` |
| 泵状态 | `water_pump`/`air_pump` | 原样推送 | `pumpPresentation()` 归一 `1/on/true → 运行中` |

`extract_history_sample(values)`：`waterlevel` 与 `humidity` **任一缺失即返回 `None`**（不落半条记录），两者齐全时 `int(float(...))` 并附毫秒 `ts`。这意味着只报 DO/Eh 的报文不会污染 `sensor_history`。

### 7.4 `connect_huawei_iot(uid)`

```
1. cfg = db.load_config(uid); 无行 -> False
2. 取 host/port(默认1883)/client_id/user/pw/device_id/target_device/m2m_topic/cmd_topic
3. 必填校验：host, client_id, user, pw, device_id 任一为空 -> False
4. _stop_client(uid)                                   # 重连前先停旧连接
5. try: mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=...)
   except AttributeError: mqtt.Client(client_id=...)    # paho < 2.0 兼容
6. user_data_set({uid, m2m_topic, cmd_topic, target_device, device_id})
7. username_pw_set(user, pw)
8. 挂 on_connect / on_disconnect / on_message
9. connect(host, port, 60) + loop_start()
   except -> disconnect() + return False
10. mqtt_clients[uid] = {client, device_id, cmd_topic, connected: False}
11. return True
```

`CallbackAPIVersion.VERSION2` 的兼容处理是关键：paho-mqtt 2.x 强制要求显式回调版本，1.x 没有该常量，`AttributeError` 回退覆盖两个大版本。注册表里 `connected` 初始写 `False`，只有 `on_connect` 收到 `rc==0` 才置 `True`——这保证前端看到的"已连接"是 broker 真实握手结果，而不是"我们发起了连接"。

**订阅列表**

| Topic | 用途 | 备注 |
|---|---|---|
| `m2m_topic`（默认 `/esp32e/data`） | 接收数据转发规则推送的 ESP32-E 上报 | 非 `$oc` 自定义 Topic |
| `$oc/devices/<device_id>/user/#` | 接收平台侧命令响应/属性设置回执 | `device_id` 为空时跳过订阅 |

### 7.5 `send_property_command(uid, props)`

```
1. device, action = next(iter(props.items()))          # 只支持单属性单值
2. entry = get_client(uid); 无记录或未 connected -> False
3. cmd_topic = entry.cmd_topic or DEFAULT_CMD_TOPIC
4. message = json.dumps({'device': device, 'action': action}, ensure_ascii=False)
5. cli.publish(cmd_topic, message)
6. return True
```

`publish` 是异步的（QoS 0，不等 PUBACK），因此返回 `True` 只代表"已交给 paho 发送缓冲"，不代表设备已执行。这是刻意的：页面状态只反映设备真实回传的 MQTT 消息（`iot.py:382-383` 注释明确"不做任何模拟回执"）。

### 7.6 华为云 Topic 与数据转发规则对照

| 方向 | Topic | 发布方 | 订阅方 | 配置位置 |
|---|---|---|---|---|
| 上行（设备→云） | `/esp32e/data` | ESP32-E | 本系统（`m2m_topic`） | 华为云"数据转发规则"把设备消息转发到该 Topic |
| 上行（平台→应用） | `$oc/devices/<device_id>/user/#` | 华为云 IoTDA | 本系统 | 平台内置，无需规则 |
| 下行（应用→云） | `/esp32e/cmd` | 本系统（client 身份） | ESP32-E | 自定义 Topic，**必须**在规则中把该主题消息转发到设备 |
| 下行（应用→平台） | `$oc/devices/<id>/sys/commands/request_id=...` | — | — | **不使用**：未在产品中定义会报 `IOTDA.017004 Invalid topic` |

`iot.py:378-383` 记录了这个坑：应用侧必须用**非 `$oc` 的自定义 Topic** 下发，再靠规则转发，且应用要以 client 身份连接，不能抢占 ESP32-E 的身份（否则设备被踢下线）。

## 8 告警与推送详细设计（`qinghe/alerts.py`）

### 8.1 `evaluate_alerts` 判定表

纯函数，签名 `evaluate_alerts(soil_pct, water_mm, humi_lower, humi_upper, water_upper, rori=None) -> list`，返回 `[{'level','msg'}]`。

| 序号 | 条件 | `level` | 文案模板（逐字） |
|---|---|---|---|
| 1 | `soil_pct < humi_lower` | `warn` | `土壤湿度过低 %.1f%% < 下限 %.1f%%，建议补灌` |
| 2 | `elif soil_pct > humi_upper` | `warn` | `土壤湿度过高 %.1f%% > 上限 %.1f%%，注意排湿` |
| 3 | `water_mm > water_upper`（独立 if） | `warn` | `水位过高 %.1fmm > 上限 %.1fmm，注意排水` |
| 4 | `rori is not None and rori >= 70` | `danger` | `RORI %.0f 重度厌氧，强制增氧` |
| 5 | `elif rori >= 40` | `warning` 级判定但返回 `warn` | `RORI %.0f 中度缺氧，脉冲加气` |

三点必须注意：① 土壤过低与过高是 `elif`，**互斥**；② 水位告警是独立 `if`，可与土壤告警并存；③ **没有"水位过低"告警**——低水位由自动调控开泵处理，不打扰用户。这一缺失导致 `alert_center.ALERT_CODES` 中的 `water_low` 码在实际运行中无人产生（见第 16 章）。

### 8.2 `AlertDeduper` 冷却算法

```
should_emit(key, now=None):
  1. now = time.time() if now is None else now
  2. with self._lock:
  3.     last = self._last.get(key)
  4.     if last is not None and now - last < self.cooldown: return False
  5.     self._last[key] = now
  6.     return True
```

| 项 | 值 |
|---|---|
| 冷却时长 | `cooldown=config.ALERT_COOLDOWN_SECONDS=60` 秒 |
| 键 | 调用方决定；`alert_center` 用 `'%d|%s|%s' % (uid, code, content)` |
| 状态 | `_last: dict` + `threading.Lock` |
| 重置 | `reset()` 清空（切库/测试隔离时调用） |

语义是"同一 key 60 秒内只放行一次"，且**放行时立即刷新时间戳**，因此持续存在的告警每 60 秒最多提醒一次，不会因为用户忽略而停止提醒。

### 8.3 `notify_webhook`

```
1. cfg = db.load_config(uid); 无行或无 webhook_url -> False
2. url 必须 startswith('http://') 或 'https://'，否则 False
3. text = '【青禾智灌系统】' + title + '\n' + content
4. payload = {'msgtype':'text', 'text':{'content': text}}
5. POST url, json=payload, timeout=6
6. return r.status_code in (200, 201)
7. 任何异常 -> False
```

| 要点 | 说明 |
|---|---|
| 载荷格式 | 钉钉/企业微信/飞书通用的 `msgtype=text` 结构 |
| 关键词 | 钉钉机器人"自定义关键词"安全设置要求正文含 `【青禾智灌系统】`，故 `ALERT_KEYWORD` 固定前置 |
| 超时 | `TIMEOUT_WEBHOOK=6` 秒，避免慢 webhook 拖住请求栈 |
| 失败降级 | 返回 `False`，调用方 `/api/notify_alert` 变成 `{'status':'skipped','sent':false}`，HTTP 仍 200 |
| 重试 | `alerts` 层**不重试**；重试在 `alert_center._push_with_retry` 里做（2 次，0.5 s/1.0 s 退避） |

## 9 实时通道详细设计（`qinghe/realtime.py`）

### 9.1 房间模型

```
浏览器 A (uid=1) ── SocketIO ──┐
浏览器 B (uid=1) ── SocketIO ──┼── room "1" ── emit_hw_data(uid=1, ...)
浏览器 C (uid=2) ── SocketIO ──┴── room "2" ── emit_hw_data(uid=2, ...)
```

房间名就是 `str(uid)`，`connect` 时 `join_room(str(uid))`。多标签页/多设备登录同一账号会进入同一房间，因此**同一用户的所有终端看到同一份实时数据**；跨用户严格隔离，`emit_hw_data` 只能发往指定房间。

### 9.2 `connect` 与 `send_command`

```
on_ws_connect():
  1. uid = session.get('user_id'); 无 -> return False（拒绝握手）
  2. join_room(str(uid))
  3. iot.connect_huawei_iot(uid)                      # 每次连接都尝试重建 MQTT
  4. status = 'online' if iot.is_connected(uid) else 'offline'
  5. emit_hw_data(uid, {'type':'device_status','status':status})

on_ws_command(data):
  1. uid = session.get('user_id'); 无 -> return（静默丢弃）
  2. prop = PROP_MAP.get(data.get('device')); 无 -> return
  3. action = data.get('action')
  4. iot.send_property_command(uid, {prop: 'on' if action == 'on' else 'off'})
```

第 3 步的 `connect_huawei_iot` 在 WebSocket 事件线程里执行，含 TCP 建连，可能耗时秒级。这是已接受的代价：只有页面首次打开时才触发，且换取了"配置改完刷新页面即生效"的体验。

### 9.3 白名单

```
PROP_MAP = {'water_pump': 'water_pump', 'air_pump': 'air_pump'}
```

白名单是"设备名 → 物模型属性名"的映射，当前两者同名。它的存在不是为了改名，而是**拒绝任意属性透传**：若直接把 `data['device']` 拼进下发报文，攻击者可通过 WebSocket 下发任意属性（如篡改阈值、触发固件动作）。`send_command` 只接受这两个键，其余静默丢弃（不返回错误，避免给探测者反馈）。

同样的白名单在 `routes/app_routes.py:14` 又定义了一份，供 `POST /api/app_send_command` 使用。两份重复是当前状态，存在漂移风险（第 16 章登记）。

### 9.4 前后端事件契约

| 方向 | 事件名 | 载荷 | 触发时机 | 前端处理 |
|---|---|---|---|---|
| 下行 | `hw_data` | `{'type':'device_status','status':'online'|'offline'}` | MQTT 连接/断开、WS 握手 | 置 `S.cloudConnected`，`enqueueFlag('refreshStatus')` |
| 下行 | `hw_data` | `{'type':'data','topic':'waterlevel'|'humidity'|'do'|'eh'|'water_pump'|'air_pump'|'humi_up'|'humi_down'|'waterlevel_up'|'waterlevel_down'|'log','payload':'...'}` | 每条 MQTT 报文按属性拆分 | 按 `topic` 分支更新内存态并入 DOM 队列 |
| 下行 | `hw_data` | `{'type':'data','topic':'log','payload':'华为云 MQTT 连接成功'}` | `on_mqtt_connect` 成功 | 追加运行日志 |
| 上行 | `send_command` | `{'device':'water_pump'|'air_pump','action':'on'|'off'}` | 手动按钮 / 自动调控 | 服务端校验白名单后下发 MQTT |

`payload` 一律是**字符串**（`str(v)`），因此数值要前端 `parseFloat`；这也让 `log` 类纯文本可以复用同一结构。前端对 `payload` 先尝试 `JSON.parse`，成功则按对象取值（兼容设备一次性上报整个 JSON），失败则当标量用——这就是 `pickValue()` 的存在理由。

## 10 天气与 AI 详细设计

### 10.1 `photon_reverse` 与 `_pick_admin`

Photon（komoot/OSM）免 Key、返回简体、可下探到社区级，缺点是行政层级字段可能为 `None` 或重复。

```
_pick_admin(values):
  1. 过滤空值与 '中华人民共和国'/'中国'
  2. 按原顺序去重（保持 大->小）
  3. return out[-4:]                     # 只要最细的 4 级

photon_reverse(lat, lng):
  1. GET https://photon.komoot.io/reverse?lat=&lon=&lang=zh, timeout=6
  2. features[0].properties -> f；f 为空 -> None
  3. chain = _pick_admin([state, city, county, district, suburb, quarter])
  4. name 存在且不在 chain 中 -> chain.append(name)     # 社区/村/POI 补到末尾
  5. chain = chain[-4:]；空 -> None
  6. return ' · '.join(chain)
```

`out[-4:]` 而不是 `out[:4]` 是刻意的：Photon 的 `state`（省）粒度太粗，用户要的是"市·区·街道·社区"，取尾部 4 级正好。`name` 去重后再 append，避免出现"西湖区 · 西湖区"。

### 10.2 `fetch_forecast` 与 URL 拼接

```
build_forecast_url(domain, lng, lat, key):
  domain = (domain or DEFAULT_WEATHER_DOMAIN).strip()
  return 'https://%s/v7/weather/7d?location=%s,%s&key=%s' % (domain, lng, lat, key)
```

| 场景 | 返回 |
|---|---|
| 请求异常 | `{'code':'ERR','error':'天气接口请求失败: <原因>'}` |
| 响应非 JSON | `{'code':'ERR','error':'天气接口非 JSON（HTTP <code>）'}` |
| 正常 | 上游 JSON 原样透传（含 `code:'200'`、`daily[]`） |

天气接口是**代理**而非透传给浏览器：一是避免前端暴露 `weather_key`，二是绕过 CSP 的 `connect-src` 限制。上游异常不抛，而是包装成 `code:'ERR'` 让前端降级为"无预报"（此时 `compute_dynamic_threshold` 收到空列表，退化为原始阈值）。

### 10.3 `geo_lookup` 缓存

| 项 | 实现 |
|---|---|
| 缓存键 | `geo_key(lat, lng) = '%s,%s' % (round(lat,4), round(lng,4))`，4 位小数约 11 m 精度 |
| 命中 | `db.get_geo_cache(key)` 非空 → 返回 `(name, True)` |
| 未命中 | `photon_reverse()` → 成功则 `db.set_geo_cache()` 并返回 `(name, False)`；失败返回 `(None, False)` |
| 失败不缓存 | 兜底文案 `geo_fallback_text()` 由路由层生成，**不入缓存**，便于下次重试 |
| 表不存在 | `get_geo_cache` 捕获 `sqlite3.Error` 返回 `None`，不炸 |

### 11.4 四个高风险接口的展开步骤

**① `POST /api/save_config`（全量覆盖，最易出错）**

```
1. 无 session -> 401
2. old = db.load_config(uid) 转 dict（无行则 {}）
3. for col in db.CONFIG_COLUMNS:  v = data.get(col)
        if v == config.MASK or v is None: v = old.get(col)   # 掩码/缺省 = 不改
4. port = _to_int(data.get('iot_port'))
   if port is None or not (1 <= port <= 65535):
        port = _to_int(old.get('iot_port'), 1883)
        if not (1 <= port <= 65535): port = 1883
5. values['iot_port'] = port
6. db.save_config(uid, values)        # 21 列全量 UPDATE，缺键写 NULL
7. iot.connect_huawei_iot(uid)       # 无论成败都重连
8. return {'status':'success','message':'配置已更新'}
```

风险点：前端漏传任一列 → 该列被写成 `NULL`。例如漏传 `pump_port`，则 `pump_port` 变 `NULL`，前端下拉框空白。这是"全量覆盖"语义的必然代价，前端必须回传完整表单。

**② `POST /api/app_login`（限流 + 签发 + 建连）**

```
1. username.strip() / password
2. auth._login_locked(username) -> 429
3. user, ok = auth.authenticate(username, password)
4. ok: _clear_login_fail; token = issue_token(user['id']); iot.connect_huawei_iot(user['id'])
5. fail: _record_login_fail; 200 '账号或密码错误'
```

注意第 4 步的 `connect_huawei_iot` 在登录请求内同步执行，MQTT 服务器不可达时会拖慢登录响应（`connect()` 默认超时）。这是已接受的取舍：App 登录后立即可下发指令。

**③ `POST /api/plan/confirm`（状态机 + 多设备下发）**

```
1. plan_id 解析失败 -> 400
2. result = planner.confirm_plan(uid, plan_id)
3. 校验顺序：归属 user_id -> status == 'pending' -> ts 距今 <= PLAN_TTL_SECONDS(600)
   任一不满足 -> {'ok': False, 'error': ...}
4. 超时：UPDATE status='expired'，返回 ok=False
5. 逐条动作：只允许 ALLOWED_DEVICES=('air_pump','water_pump') 与 ALLOWED_ACTIONS=('on','off')
6. iot.send_property_command(uid, {device: action})，失败的进 failed
7. UPDATE status='confirmed', decided_ts=now, apply_result=json
8. logbook.add_log(uid, ..., source='plan'); alert_center.push_alert(uid,'info','auto_action', ...)
9. return {'ok': bool, 'applied': [...], 'failed': [...]}
```

**④ `GET /api/export/history.csv`（列探测）**

```
1. uid 校验
2. limit = _parse_limit(raw, DEFAULT_EXPORT_ROWS=5000)；非法 -> 400
3. since_ts = _parse_int(raw, 0, 0, 2**62)；非法 -> 400
4. columns = _table_columns(conn, 'sensor_history')      # PRAGMA table_info
5. selected = [c for c in ('ts','water_adc','soil_adc','do_mgl','eh_mv') if c in columns]
6. SELECT selected FROM sensor_history WHERE user_id=? AND ts>=? ORDER BY ts DESC LIMIT ?
7. 每行 -> [时间串, ts, water_adc, soil_adc, do_mgl空, eh_mv空]
8. text = BOM + CSV；响应头 Content-Type: text/csv、Content-Disposition、Cache-Control: no-store
```

第 5 步的列探测让接口在旧库（无 `do_mgl/eh_mv`）上仍能工作，代价是这两列**当前恒为空**（见第 16 章）。

## 12 新增功能模块详细设计（NF1–NF7）

七个模块共享三条约定：① **懒建表**——不在 `init_db()` 里建，首次公开函数入口调用 `_ensure_schema()`，用模块级 `_schema_ready` + `_schema_lock` 双检；② **不修改既有 12 个文件**，只用 `db.get_db()` 与 `config` 常量；③ **外部调用必带 timeout，异常不抛到请求栈**。

懒建而非集中建的理由：新增模块与 `db.init_db()` 由不同人并行开发，集中建表会把两个分支的合并点变成冲突点；懒建让模块自包含，且测试可以只导入被测模块。

### 12.1 NF1 告警中心 `qinghe/alert_center.py`

| 项 | 内容 |
|---|---|
| 模块文件 | `qinghe/alert_center.py`（328 行） |

| 函数签名 | 入参 | 返回 | 要点 |

**关键算法：去重键与码映射**

```
push_alert(uid, level, code, content):
  1. level = _normalize_level(level)     # warn->warning, critical/fatal/error->danger, 未知->info
  2. code  = _normalize_code(code)       # 空 -> 'auto_action'
  3. content = _clip_content(content)    # 超 500 截断
  4. key = '%d|%s|%s' % (uid, code, content)
  5. 每次读取 config.ALERT_COOLDOWN_SECONDS 覆盖 _deduper.cooldown   # 便于测试调小
  6. if not _deduper.should_emit(key): return {'id': _last_ids.get(key,0), 'deduped': True, 'pushed': False}
  7. alert_id = _insert_alert(uid, level, code, content)
  8. _last_ids[key] = alert_id
  9. 起 daemon 线程 'alert-push'：_push_with_retry(uid, 标题, content)
 10. return {'id': alert_id, 'deduped': False, 'pushed': True}
```

`_code_for_message()` 用**正文前缀**反推 code（`土壤湿度过低`→`soil_low`、`水位过高`→`water_high`、`RORI` 前缀按 level 分 `rori_high`/`rori_medium`）。这是为适配 `alerts.evaluate_alerts()`——它只返回 `{level,msg}` 不含 code，而 `alerts` 表要求 code 非空。该映射是字符串匹配，文案一改就失效，属脆弱耦合（第 16 章）。

`water_lower` 参数仅为契约对齐而保留：`evaluate_alerts()` 不产出低水位告警，传什么都不影响结果。

**时序（一次告警的完整生命周期）**

```
MQTT 回调            handle_mqtt_message       前端 tick(5s)        /api/notify_alert      alert_center        webhook
   |                       |                        |                      |                     |                 |
   |--报文-->            |                        |                      |                     |                 |
   |                       |--hw_data(emit)------>|                      |                     |                 |
   |                       |                        |--checkAlerts()      |                     |                 |
   |                       |                        |--POST /api/notify_alert----------------->|                 |
   |                       |                        |                      |--notify_webhook()-------------------->|
   |                       |                        |                      |                     |                 |
   |                       |                        |  (另一条路径) 服务端 evaluate_and_push |                 |
   |                       |                        |                      |--push_alert()------>|                 |
   |                       |                        |                      |                     |--INSERT alerts  |
   |                       |                        |                      |                     |--thread push--->|
   |                       |                        |                      |<--GET /api/alerts---|                 |
```

**异常降级**：落库失败（`sqlite3.Error`）→ 直接返回 `{'id':0,...}`，不阻断业务；webhook 失败 → 线程内 `False`，不影响 `push_alert` 返回；`_ensure_schema` 在每个公开函数入口调用，切库后自动重建。

```
_run():
  while not stop:
```

### 12.3 NF3 设备心跳 `qinghe/heartbeat.py`

| 项 | 内容 |

| 常量 | `DEVICE_OFFLINE_SECONDS=30`、`WATCH_INTERVAL=5.0`（**模块内常量，未进 `config.py`**） |

| 函数签名 | 入参 | 返回 | 要点 |
|---|---|---|---|
| `mark_seen(uid, ts=None)` | uid / 可选时间 | `None` | `UPSERT ... ON CONFLICT(user_id) DO UPDATE SET last_seen_ts, online=1, last_reason='heartbeat'` |
| `get_status(uid, offline_seconds=None)` | 阈值覆盖 | `{'online','last_seen_ts','silent_seconds'}` | `online = silent <= threshold`（**闭区间**）；无行返回 `{'online':False,'last_seen_ts':0,'silent_seconds':0}` |

| `stop_watcher()` | — | `None` | 幂等 |

**关键算法：静默秒数向上取整**

```
silent_seconds = (gap_ms + 999) // 1000
```

向上取整而非截断，是为了避免"刚好 29.6 s 被判成 29 s → 判在线"的边界抖动；配合 `<=` 比较，30.0 s 整仍在线上、30.001 s 才离线。

`mark_seen` 内 `seen_ts = min(seen_ts, now)` 防御设备时钟超前（设备 RTC 未校时会把 `ts` 报到未来），否则 `silent_seconds` 变负数、设备永远在线。

`sweep_offline` 对"由在线转离线"的 uid 会写 `last_reason='silent_timeout'` 并调用 `_emit_offline()`：`logbook.add_log(level='warning')` + `alert_center.push_alert(uid,'warning','device_offline','设备已离线，最后心跳 %d 秒前')`。注意**只有状态翻转才推送**，持续离线不会每 5 秒刷一条告警。

`start_watcher` 默认**不自动启动**：需要调用方传入 `get_uids`（内存里没有"所有用户"的概念）与 `emit`（避免模块反向依赖 `realtime`）。当前没有生产代码调用它，设备在线判定实际由前端心跳看门狗承担（第 13 章），这是双轨并存的设计冗余（第 16 章）。

**状态机**

```
                  propose_plan
                       |
                       v
                  +---------+   confirm_plan(ok)   +-----------+
                  | pending |--------------------->| confirmed |
                  +---------+                      +-----------+
                    |      |
      reject_plan   |      |  TTL 600s 超时 / 下发失败
                    v      v
             +----------+  +--------+
             | rejected |  | expired| / failed
             +----------+  +--------+
```

不可逆：`confirmed`/`rejected`/`expired`/`failed` 都是终态，再次 confirm 返回"状态不允许"。TTL 从 `plans.ts` 起算，防止"昨天生成的预案今天被误确认"。

**AI 回退策略**

```
1. ctx = build_context(uid)；组装 system+user 提示（含 ctx 的 JSON 摘要）
2. ai_used = True；调 ai.chat(domain, key, prompt)，timeout=25
3. 若 无 key / 异常 / 返回非 JSON / 缺 actions 字段：
      ai_used = False；走 _rule_based_plan(ctx) 生成动作
4. actions 逐条过滤：device ∈ ALLOWED_DEVICES 且 action ∈ ALLOWED_ACTIONS，非法项丢弃
5. 落库 status='pending'，返回 plan_id
```

规则回退保证"没有 AI Key 也能用"：按 RORI 档位与水位直接给出 `air_pump on/off`、`water_pump on/off`，`reasoning` 写明依据。这是该系统在校园网断网环境下的可用性底线。

### 12.5 NF5 节水减碳 `qinghe/metrics.py`

| 项 | 内容 |
|---|---|
| 模块文件 | `qinghe/metrics.py`（353 行） |
| 表与索引 | `pump_runtime(user_id, device, day, seconds, PK(user_id,device,day))` + `idx_pump_runtime_user_day(user_id, day)` |
| 常量 | `DEFAULT_CHANNEL_AREA_M2=0.5`（env `FARM_CHANNEL_AREA_M2`）、`DEFAULT_CH4_SAVED_G_PER_HOUR=0.8`（env `FARM_CH4_SAVED_G_PER_HOUR`）、`GWP100=28`、`DEVICES=('air_pump','water_pump')`、`MAX_DAYS=90` |
| 内部状态 | `_last = {(uid,device): (state, ts_ms)}` + `_last_lock`；`_schema_ready`（**bool，未按库路径**） |

| 函数签名 | 入参 | 返回 | 要点 |
|---|---|---|---|
| `note_pump_state(uid, device, state, ts=None)` | 设备/状态/时间 | `None` | 首次只记录不计时；`prev=='on'` 时结算时长 |
| `estimate(uid, days=7)` | 天数 | `{'days','water_liters','pump_minutes','air_minutes','ch4_saved_g','co2e_saved_g','method'}` | 汇总 `daily_series` |
| `daily_series(uid, days=7)` | 天数 | `list[{'day','water_liters','pump_minutes','air_minutes','ch4_saved_g','co2e_saved_g'}]` | 升序，末项为今天 |
| `channel_area_m2()` / `ch4_saved_g_per_hour()` | — | `float` | 读 env，必须 >0，否则回默认 |

**结算算法**

```
note_pump_state(uid, device, state, ts):
  1. state = _normalize_state(state)        # 1/true/on/open->on；0/false/off/close->off
  2. prev = _last.get((uid,device))
  3. _last[(uid,device)] = (state, ts)
  4. if prev is None: return                # 首次只建基线
  5. if prev.state == 'on': _add_seconds(uid, device, prev.ts, ts)
  6. （prev 为 off 时无需处理）

_add_seconds(...):
  按本地自然日切分区间，跨零点时拆成两段分别累加
  INSERT INTO pump_runtime ... ON CONFLICT(user_id,device,day)
  DO UPDATE SET seconds = seconds + excluded.seconds
```

`_water_mm_by_day` 只累计水位的**正向抬升**（回落不抵扣），并以 `ts < start_ms` 的最近一条为基线。这是工程近似：水位回落可能来自蒸发/渗漏/人工取水，抵扣会低估灌溉量。

**算例三（本章指定算例：节水减碳估算）**

某日数据：`air_pump` 累计运行 1800 s（30 min），`water_pump` 累计运行 360 s（6 min），当日水位累计正向抬升 20 mm；渠道面积 0.5 m²，减排系数 0.8 g CH₄/h，GWP100=28。

| 指标 | 公式 | 计算 | 结果 |
|---|---|---|---|
| 节水量 | `water_liters = water_mm × area` | 20 × 0.5 | **10.0 L** |
| 水泵时长 | `pump_seconds / 60` | 360 / 60 | **6.0 min** |
| 气泵时长 | `air_seconds / 60` | 1800 / 60 | **30.0 min** |
| 甲烷减排 | `air_minutes / 60 × rate` | 30/60 × 0.8 | **0.4 g CH₄** |
| 碳当量 | `ch4_saved_g × GWP100` | 0.4 × 28 | **11.2 g CO₂e** |

量纲校验：`water_mm × area` 的单位是 mm·m² = 10⁻³ m³ = 1 L，与"1 mm 雨量落在 1 m² 上等于 1 L"一致，因此 `daily_series` 里 `water_liters = water_mm * area` 无需再乘 1000（等价于 `Δmm/1000 × area × 1000`）。`method` 字段固定输出"工程估算，非实测"口径说明，避免被当成计量表读数。

### 13.1 文件与 defer 加载顺序

`templates/index.html:329-337` 的加载顺序即依赖顺序，**不可调换**：

```
1. socket.io.min.js   (CDN, defer, crossorigin)
2. chart.umd.min.js   (CDN, defer, crossorigin)
3. core.js      全局 S/QH/QH_STORE 之外的 工具函数、tick 调度器、DOM 队列
4. store.js     依赖 core（无强依赖，但需先于 charts 提供 QH_STORE）
```

全部 `defer`，因此执行时机在 DOM 解析完成后、`DOMContentLoaded` 之前；`app.js:199` 再判 `document.readyState` 决定立即 `init()` 还是挂 `DOMContentLoaded`。`login.html` 只加载 `login.js`，不加载其余脚本。

### 13.2 统一 tick 调度器

`core.js:177-217` 用**一个** `setInterval(500ms)` 驱动所有周期任务，替代原先散落的多个定时器：

| 任务名 | 周期 | 任务体 | 注册位置 |
|---|---|---|---|
| `dom` | 500 ms | `QH.flushDom()` 批量刷 DOM | `app.js:143` |
| `clock` | 1000 ms | `updateClock()` 写 `clockDisplay` | `app.js:146` |
| `chart` | 2000 ms | `renderTrendCharts()` + `pushChartPoint()`（仅 `chartDirty`） | `app.js:147` |
| `heartbeat` | 5000 ms | `watchHeartbeat()` + `checkAlerts()` | `app.js:152` |
| `persist` | 30000 ms | `STORE.flushAll(trendData, roriTrendData)` | `app.js:156` |

累加器实现：`acc[name] += dt`，达到 `every` 则执行并清零。用"实际经过时间"而非"固定步长"累加，页面被切到后台再切回时不会一次性补跑几十次任务。单任务异常被 `try/catch` 吞掉（`core.js:209`），不拖垮主循环。

### 13.3 消息队列与批量 DOM 更新

MQTT 报文可能 3 s 一条、多设备更高频。`realtime.js` 的 `hw_data` 回调**不直接写 DOM**，而是：

```
pending = {fields:{}, styles:{}, pumps:{}, flags:{}, sliders:{}}
enqueueField(key, value) / enqueueStyle / enqueuePump / enqueueFlag / enqueueSlider
       ↓ 500ms 后
flushDom(): 逐类写 DOM，然后 pending 重置；最后按 flags 触发 refreshStatus/updateRori/checkAlerts/markChartDirty
```

写 DOM 的四个原语都做"值未变不写"比对：`setText` 比 `el.__qhText`、`setAttr` 比 `el.__qhAttr_<name>`、`setStyle` 比 `el.__qhStyle_<prop>`、`toggleClass` 比 `el.__qhCls_<cls>`。效果是同一条报文即使重复到达也不会触发重排。

### 13.4 图表节流

### 13.8 断线重连与心跳看门狗

**重连**：`S.socket = io()` 使用 Socket.IO 默认策略（指数退避、无限重试、`reconnectionDelay 1s` 起）。`disconnect` 回调把 `cloudConnected` 与 `deviceOnline` 同时置 `false` 并写日志"服务器断开"，`connect` 回调写"云服务连接成功"，因此断网期间页面顶部胶囊会变红、面板进入 `panel-disabled`，恢复后自动回绿，无需用户刷新。

**心跳看门狗**（`realtime.js:170-180`）：

```
watchHeartbeat():   # 统一 tick 每 5s 调用一次
  1. if S.dataReceived: S.heartbeatMiss = 0; S.deviceOnline = true; S.dataReceived = false
  2. else: S.heartbeatMiss += 1; if S.heartbeatMiss >= S.heartbeatMissLimit: S.deviceOnline = false
  3. refreshStatus()
```

**心跳阈值核对（已核实）**：`core.js:37` 的实际值是 `heartbeatMissLimit: 4`，即 **4 × 5 s = 20 s** 无数据判离线；`realtime.js:167-168` 的注释已写明"阈值取自 core.js 的 heartbeatMissLimit，默认 4 次"，与代码**一致**。任务书曾怀疑注释为"8 次 ≈ 40 s"，实测不成立，此处记录核对结论以免后续重复排查。20 s 相对 ESP32-E 的 3 s 上报间隔，相当于容忍丢 6 帧。

另一处不一致：服务端 `heartbeat.DEVICE_OFFLINE_SECONDS=30`，前端 20 s，**前端会先判离线**。这两个阈值分属两条链路（服务端 `device_status` 表 / 前端内存态），当前不冲突，但同一块 UI 上显示"设备离线"的来源不同，排障时需注意。

## 14 部署与运行详细设计

### 14.1 开发启动：`app.py`

```
python app.py
  -> from qinghe import config, create_app
  -> app, socketio = create_app()          # 建表 + geo_cache + 注册蓝图/事件
```

`host='0.0.0.0'` 让同一局域网的同学能访问；`allow_unsafe_werkzeug=True` 是 Flask-SocketIO 对 Werkzeug 生产使用的显式放行，**仅限开发**。`FARM_DEBUG=1` 时会暴露 Werkzeug 调试器（可执行任意代码），因此 `is_debug()` 默认 `'0'`。

### 14.2 生产启动：`server.py`（waitress + threading）

```
python server.py
  1. host = get_host()      # HOST，默认 0.0.0.0
  2. port = get_port()      # PORT，非法则打印[警告]并回退 5000
  3. debug = get_debug()    # FARM_DEBUG，接受 1/true/yes/on/y/t
  4. app, socketio, hooks = load_app()   # 优先 create_app()，失败回退 from app import app
  5. run_init_hooks(hooks)               # 当前恒为空列表（工厂内已初始化）
  6. socketio.init_app(app, async_mode='threading', cors_allowed_origins='*')
  7. lan_ips = list_lan_ips()；print_banner(...)
  8. waitress.serve(app, host, port, threads=int(FARM_THREADS or 8))
     若 waitress 缺失 -> 打印双条[警告]并回退 socketio.run(...)
```

| 关键决策 | 取值 | 理由 |
|---|---|---|
| `SOCKETIO_ASYNC_MODE` | `'threading'` | MQTT 回调在后台线程 `emit`，eventlet/gevent 的 monkey-patch 会与之冲突 |
| HTTP 服务器 | waitress | 纯 Python、Windows 友好、多线程 WSGI |
| 线程数 | `FARM_THREADS` 默认 8 | 校园网小规模足够；MQTT 回调走独立线程不受影响 |
| `load_app()` 回退 | `from app import app, socketio` | 工厂不可用时仍能起服务；**不导入** `init_db`（`app.py` 没有这些名字，会 ImportError） |

**局域网地址横幅**：`_iter_ipv4_candidates()` 先用 UDP `connect(('8.8.8.8',80))` 拿系统选路地址（不发包），再用 `getaddrinfo` 枚举多网卡；`is_usable_lan_ip()` 过滤回环、`169.254/16` 链路本地、组播、未指定、保留段；`list_lan_ips()` 按 `10.x → 172.16-31 → 192.168 → 其它` 排序，第一个打上"← 把这个地址发给同学"。

| 进程日志 | 标准输出（waitress/print），建议由 systemd/计划任务重定向到文件并轮转 |

## 16 待复核假设与缺陷

以下为撰写本文时对源码的实测发现。**未修改任何代码**，按严重度排列，供后续修复排期。

| 编号 | 严重度 | 位置 | 现象 | 影响 | 建议 |
|---|---|---|---|---|---|
| D-01 | 高 | `qinghe/routes/export_routes.py:134` | 导出历史时选择列含 `do_mgl`、`eh_mv`，但 `sensor_history` 表 DDL（`db.py:75-81`）只有 `water_adc`、`soil_adc` | CSV 最后两列**恒为空**，下游按固定表头解析会误以为"传感器未上报" | 要么给 `sensor_history` 扩列并落库 DO/Eh，要么从表头移除这两列 |
| D-02 | 中 | `qinghe/routes/config_routes.py` 调用 `iot.connect_huawei_iot(uid)` | 保存配置后在**请求线程内同步**建连，`mqtt.Client.connect(host, port, 60)` 最长阻塞 60 s | 华为云不可达时 `/api/save_config` 卡住，前端"保存中"转圈直至超时；并发保存会占满 waitress 线程池（默认 8） | 改为后台线程重连并立即返回"配置已保存，正在重连"；或把 `connect` 超时降到 5 s |
| D-03 | 中 | 服务端 `heartbeat.DEVICE_OFFLINE_SECONDS=30` vs 前端 20 s | 两条链路离线判定阈值不一致 | 同一 UI 上"设备离线"来源不同，排障易误判；且 `start_watcher()` 当前**无生产调用点**，服务端 `device_status` 表不会自动更新 | 统一阈值并明确单一权威来源；或在前端展示服务端 `get_status` 结果 |
| D-04 | 中 | `qinghe/alert_center.py:283 _code_for_message` | 用中文文案前缀反推 `code`（"土壤湿度过低"→`soil_low`） | 一旦 `alerts.evaluate_alerts()` 文案改动，映射静默失效，全部落到默认 `auto_action` | 让 `evaluate_alerts()` 直接返回 `code`，或引入稳定枚举 |
| D-05 | 中 | `qinghe/alerts.py` `evaluate_alerts()` | 只产出土壤过低/过高、水位过高、RORI 三档告警，**不产出"水位过低"**；而 `alert_center._code_for_message()` 保留了 `'水位过低' → water_low` 的映射分支 | `water_low` 无自动触发路径，只能靠调用方手动 `push_alert`，告警类型覆盖不全 | 明确"低水位由自动开泵处理、不告警"的决策并删码，或在 `evaluate_alerts` 补 `water < water_lower` 分支（`evaluate_and_push` 已预留 `water_lower` 形参） |
| D-06 | 低 | `qinghe/routes/app_routes.py:14` 与 `qinghe/realtime.py:14` | `PROP_MAP` 白名单定义两份 | 新增设备时易只改一处，导致 HTTP 能下发而 WebSocket 不能（或反之） | 收敛到单一模块（如 `qinghe/iot.py`）导出 |
| D-07 | 低 | `qinghe/routes/data_routes.py:47` | `/api/forecast` 未配 Key 返回 200 + `code:'ERR'` | 与"非法入参 4xx"约定偏离，前端需特判 | 若要保持页面不报错可保留，但需在接口文档显式声明 |
| D-08 | 低 | `qinghe/metrics.py:50` | `_schema_ready` 仅 `bool`，未按库路径（`alert_center`/`logbook`/`heartbeat` 已按路径） | 测试中切换 `FARM_DB_PATH` 后可能跳过建表，导致 `no such table: pump_runtime` | 照搬 `_schema_path` 双检写法 |
| D-09 | 低 | `qinghe/routes/auth_routes.py:39,43,47` | 跨模块调用私有函数 `auth._login_locked` / `_clear_login_fail` / `_record_login_fail` | 私有接口被外部依赖，重命名即破坏 | 在 `auth.py` 提供公开包装（如 `login_throttle(name)->str|None`） |
| D-10 | 低 | `qinghe/autocontrol.py` 与 `static/js/realtime.js:121` | 前端与服务端各有一套自动调控，同时开启会互相下发相反指令 | 泵可能被两边来回切换 | 二选一并默认关闭另一方；当前 `enabled` 默认 `False` 已部分规避 |
| D-11 | 低 | `qinghe/planner.py` / `metrics.py` / `autocontrol.py` | 运行态存进程内存（`_latest`、`_last`、`state_json` 缓存） | 多进程部署（多 worker）下状态不一致 | 单进程多线程部署下无影响；上多进程前外移到 DB/Redis |
